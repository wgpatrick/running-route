# Verification, not generation, gates AI mechanical engineering

As of November 2026, a team of one to three people can assemble every stage of a CAD-to-simulation-to-manufacturing pipeline from open-source parts that run headless in Linux containers, but nobody has publicly shown an agent running the whole chain correctly. The workable open stack is build123d or CadQuery on the OpenCASCADE (OCCT) kernel for geometry, Gmsh for meshing, CalculiX for structural analysis, a slicer command line for 3D printing, and FreeCAD's CAM workbench for milling. The binding constraint is correctness: agents now produce runnable CAD code and runnable simulations most of the time, yet the closest open reference pipeline (Hephaestus-CCX: CadQuery to Gmsh to CalculiX) recorded **zero strict-passing designs in 400 first attempts** by frontier coding agents ([arXiv 2605.17448](https://arxiv.org/pdf/2605.17448)). The same gap shows up in simulation, where one benchmark saw executable solver calls 88% of the time while only a single problem passed its 10% accuracy cut, and that one by exporting a solver default value ([FEABench](https://arxiv.org/abs/2504.06260v1)). Both results were verified against the primary pages. The product to build is therefore a verification harness around Claude: kernel-level geometric tests, deterministic physics checks, an independent reviewer and human sign-off. A better generator matters less. CAM is the least mature stage: no agent results or benchmarks for toolpath generation were found, and the open tooling for cut simulation is thin. The recommended order is single-part CAD with executable geometric checks, then linear static FEA against closed-form answers, then 3D printing, then flat-part and 2.5D milling behind a human gate, with assemblies and CFD last.

## B-rep on OpenCASCADE is the only open route to STEP, and it is brittle where agents are weakest

### Representation choice follows from what CAM and FEA consume

Boundary representation (B-rep) is the only one of the three geometry families that natively yields the STEP solids with analytic faces that CAM and CAE tools expect. Implicit kernels do not: the author of the Fidget implicit kernel states it cannot export STEP because STEP files describe trimmed surfaces, a different underlying representation (reported, [HN thread](https://news.ycombinator.com/item?id=42634624)). The commercial implicit tool nTop reaches STEP only through a quad-mesh conversion that its own documentation says should not be used for lattices, with a separate implicit-to-CAD route still in beta (reported, [nTop support](https://support.ntop.com/hc/en-us/articles/7323484481555-How-to-export-geometry-as-a-CAD-part-STEP-or-Parasolid)). Mesh-based constructive solid geometry is robust for booleans, and the Manifold library became OpenSCAD's default backend in August 2025 (reported, [OpenSCAD commits](https://github.com/openscad/openscad/commits/master/)), but it outputs tessellations only. The researchers' inference is that B-rep should be the primary representation, with mesh or implicit methods confined to regions such as lattices that break B-rep kernels, accepting that those regions will not export cleanly. No source was found on how CAM tools handle mesh-derived or implicit geometry, and no quantitative robustness comparison between OCCT, Parasolid, ACIS and Zoo's engine was found.

### The headless shortlist is build123d, CadQuery and FreeCAD

OCCT 8.0.0 shipped in May 2026 with more than 500 changes since 7.9.0 and a new topology graph layer called BRepGraph (reported, [OCCT release discussion](https://github.com/Open-Cascade-SAS/OCCT/discussions/1275)). Adoption is uneven. **build123d v0.13.0 moved to OCCT 8.0.1** after four releases between June and September 2026, each with breaking API changes, and it has not reached a stable 1.0 ([build123d releases](https://github.com/gumyr/build123d/releases)). CadQuery's latest release is 2.8.0, while the last dependency pin the researchers saw (for 2.7.0) targets OCCT 7.8.x (reported, [CadQuery releases](https://github.com/CadQuery/cadquery/releases)). FreeCAD 1.1 was released on 24 March 2026, with 1.1.1 following on 15 April ([FreeCAD release notes](https://wiki.freecad.org/Release_notes_1.1), [FreeCAD blog](https://blog.freecad.org/2026/04/15/freecad-1-1-1-released/)). It is the only open option with a feature tree, assemblies, drawings, FEM and CAM in one scriptable package. Among Rust kernels, Fornjot was archived on 19 June 2026 with a README saying its goals were never reached ([Fornjot repo](https://github.com/hannobraun/fornjot)); the truck kernel was not researched. Licences for most of these libraries were not confirmed from sources in this research and should be checked before commercial use.

Commercial kernels reach a small team only as metered cloud services. Zoo's proprietary GPU engine bills $0.50 per minute of API time, metered per second since 30 September 2025 and including calls under 10 seconds since 14 October 2025, after a monthly included-usage credit that varies by plan (verified against the primary page, [Zoo billing post](https://zoo.dev/blog/per-second-billing), [Zoo API pricing](https://zoo.dev/api-pricing)). That September 2025 post puts the Free plan's credit at $10 a month, about 20 minutes, and the $20-a-month Plus plan's at $50, about 100 minutes; no Zoo page read supports a 40-minute free allowance. The current plan table loads client-side and could not be read, so today's allowances are unverified. The originally cited [Zoo Design API](https://zoo.dev/design-api) URL now redirects to the API reference and carries no prices. Onshape caps API calls annually per account and returns HTTP 402 once the cap is exhausted ([Onshape API limits](https://onshape-public.github.io/docs/auth/limits/)); third-party figures put the caps at 2,500 to 10,000 calls per user per year (secondary, [toolkit notes](https://github.com/SergeyMokhov/onshape-api-toolkit/blob/main/docs/08-rate-limits-and-errors.md)). Autodesk's Fusion Automation API became generally available on 19 May 2025 at 3.0 Flex tokens per processing hour, with file-transfer time counted (verified against the primary page, [APS blog](https://aps.autodesk.com/blog/design-automation-api-fusion-now-generally-available)); that is the launch rate, and the current rate could not be checked because Autodesk's pricing page sits on a host that is still blocked. The researchers infer that per-second metering and annual call caps both conflict with an agent loop that rebuilds geometry hundreds of times per task, which a local OCCT stack does at no marginal cost.

### No head-to-head language study exists, and executability misleads

No study compares CadQuery, build123d, OpenSCAD and Zoo's KCL under identical conditions, and no benchmark including KCL was found. Most benchmarks are CadQuery-only, which makes CadQuery the best-covered target for raw generation; RealCADBench, which has models write FreeCAD Python, and the tool-agnostic CADGenBench are exceptions. One agent paper, CADDesigner, ran CadQuery and build123d in the same framework on 200 models. build123d gave the highest first-attempt pass rate (Pass@1 of 0.59 against 0.50 for CadQuery) and the shortest latency (363 against 541 seconds) but a lower IoU (0.262 against 0.283), and the authors note that executable code does not imply geometric accuracy (verified against the primary page, v6, [arXiv 2508.01031](https://arxiv.org/abs/2508.01031)). The paper's own representation layer on top of CadQuery beat both on IoU, so this is not a clean head-to-head. P3D-Bench's first version reported that scores fell further on CadQuery than on OpenSCAD (a mean of 0.057 against 0.023 across geometry, topology and judge scores) when the same cases were posed as assemblies instead of single images (corrected: this is an assembly-versus-image comparison, not a geometry-score gap between the languages, and the passage is absent from the current v4, [arXiv 2606.11152](https://arxiv.org/html/2606.11152v1)). That benchmark also does not penalise OpenSCAD's lack of STEP output. The durable finding across benchmarks is that running code is a poor proxy for correct geometry: on Text2CAD-Bench the domain-specific Text2CAD model had the lowest invalidity rate (2 to 11% depending on level and prompt style) yet IoU of only 0.03 to 0.08 (corrected from "7.0% invalid, IoU 0.05", a figure that is not in the paper; verified against the primary page, [arXiv 2605.18430](https://arxiv.org/html/2605.18430v1)).

### Face identity, fillets and drawings are the standing pain points

Face and edge identity is the central unsolved problem in open code-CAD. build123d has no persistent naming: an open issue lists the failure cases for tags when faces split, merge or are consumed by a fillet ([build123d issue #1454](https://github.com/gumyr/build123d/issues/1454)), and a practitioner describes index-based selection as extremely brittle (anecdotal, [HN thread](https://news.ycombinator.com/item?id=47567242)). FreeCAD's 1.1 notes describe continued "mitigation" of topological naming, not a fix (reported, [FreeCAD wiki](https://wiki.freecad.org/Topological_naming_problem/en)). OCCT fillets also extend automatically along tangent-continuous edges, so a selection can fillet more than intended (reported, [OCCT modelling guide](https://occt3d.com/dev/doc/overview/html/occt_user_guides__modeling_algos.html)). The researchers' recommended mitigation, which is inference, is to regenerate the whole model from source each time, select faces by geometric predicates (position, normal, type, size), verify the selection count, and apply fillets, chamfers and shells late with fallback logic.

Tolerancing and drawings are the weakest part of the open stack. OCCT can write GD&T into STEP AP242 through its XDE module ([OCCT XDE guide](https://dev.opencascade.org/doc/overview/html/occt_user_guides__xde.html)), but users report exported annotations not being recognised by the NIST viewer or Autodesk Inventor ([OCCT forum](https://dev.opencascade.org/content/exported-pmi-graphical-presentation-step-not-picked-other-cad-tools)). No sources were found on GD&T support in CadQuery or build123d, or on FreeCAD's drawing workbench running headless.

### Vendor MCP servers exist but assume a desktop or a subscription

Autodesk, PTC and Zoo all ship Model Context Protocol servers, though the details here come from third-party guides that disagree with each other and were not checked against vendor documentation. Fusion reportedly includes a local MCP server since May 2026 that runs only while the desktop app is open (secondary, [Leo AI comparison](https://www.getleo.ai/blog/cad-mcp-server-comparison-2026)), and Autodesk also describes a cloud-hosted "Fusion Compute MCP" covering design and CAM setup ([Autodesk blog](https://www.autodesk.com/products/fusion-360/blog/fusion-compute-mcp/)). Onshape's server is hosted, in early access, and focused on writing FeatureScript (secondary, [TechDraw AI](https://techdrawai.com/blog/connect-claude-to-onshape)). The most-starred FreeCAD server, neka-nat/freecad-mcp, requires an add-on inside a running FreeCAD instance, and star counts vary by source from about 1,700 to about 2,900 (secondary, [ChatForest review](https://chatforest.com/reviews/cad-3d-modeling-mcp-servers/)). One guide found no maintained CadQuery MCP server worth listing (secondary, [buildcad.ai](https://buildcad.ai/guides/cad-mcp-servers)). The researchers infer this absence is expected: an agent with a Python sandbox can call the library directly.

## Specialists saturate sketch-and-extrude benchmarks while single-shot frontier models score near 0.4 on real parts

### Research moved from command sequences to CadQuery code, then to agent loops

Text-to-CAD research has passed through three phases. Early systems such as DeepCAD and Text2CAD (NeurIPS 2024) trained transformers to emit bespoke command sequences. From 2025, small fine-tuned language and vision models emitted CadQuery Python instead: CAD-Recode trained a 1.5-billion-parameter model on one million procedurally generated programs and reported IoU rising from 77.6% to 92.0% on DeepCAD over the prior best, with under 1% invalid outputs (verified against the arXiv version of the paper, [arXiv 2412.14042](https://arxiv.org/abs/2412.14042); the originally cited [ICCV copy](https://openaccess.thecvf.com/content/ICCV2025/papers/Rukhovich_CAD-Recode_Reverse_Engineering_CAD_Code_from_Point_Clouds_ICCV_2025_paper.pdf) is on a blocked host). cadrille added reinforcement learning on geometric reward and reported, on DeepCAD, 92.2% IoU from multi-view images and 90.2% from point clouds, both with 0.0% invalid outputs (corrected: the report had attached the point-cloud figure to images; verified against the primary page, v3, [arXiv 2505.22914](https://arxiv.org/html/2505.22914)). CADEvolve (February 2026) grew 46 hand-written primitives into about 8,000 complex parametric generators and, after augmentation, about 1.3 million scripts covering the full CadQuery operation set (verified against the primary page, [arXiv 2602.16317](https://arxiv.org/abs/2602.16317)). The two levers with the clearest measured effect are synthetic data scale and execution-based reinforcement learning. Cross-paper comparison is unsafe, because scores depend on each paper's alignment, normalisation and choice of mean or median distance. That caution is the researchers' inference: CADFit documents its own protocol (rigid alignment with global scale, normalisation to a fixed box, median results) but does not itself make the cross-paper claim ([CADFit, arXiv 2605.01171](https://arxiv.org/abs/2605.01171)).

From 2026 the frontier is the generate-execute-critique loop. CADSmith pairs exact kernel measurements with multi-view renders (reported, [alphaXiv](https://www.alphaxiv.org/abs/2603.26512v1)); the Physics-in-the-Loop system adds a structural reviewer that runs FEA ([IJCAI 2026](https://ijcai.org/proceedings/2026/714)); AssemCAD targets assemblies with articulated joints ([arXiv 2607.05123](https://arxiv.org/html/2607.05123v1)); and Pointer-CAD attacks the topology-reference problem behind fillets and chamfers ([arXiv 2603.04337](https://arxiv.org/pdf/2603.04337)). The researchers did not read these papers in full; the verification pass confirmed the CADSmith, AssemCAD and Pointer-CAD descriptions against their arXiv pages.

### Legacy datasets test little of real mechanical design

The standard training corpora have a narrow vocabulary. DeepCAD (roughly 178,000 models) and the Fusion 360 Gallery contain sketch-and-extrude operations only; the ABC dataset's one million models have no construction history; and Text2CAD's annotations are template-generated on DeepCAD geometry (verified against the primary page, [Text2CAD-Bench](https://arxiv.org/html/2605.18430v1)). The counts of 8,625 Fusion 360 Gallery sequences and roughly 660,000 Text2CAD annotations do not appear in that paper and are unverified background. A model evaluated only on these has not been tested on fillets, chamfers, revolves, sweeps, lofts, shells, sheet metal or assemblies (inference). A 2026 wave of benchmarks closes part of that gap. BenchCAD offers 17,900 execution-verified CadQuery programs across 106 industrial part families ([arXiv 2605.10865](https://arxiv.org/abs/2605.10865)); MUSE scores multi-component assemblies, in its first version on function, manufacturability and assemblability through a vision-model judge, and since its October 2026 revision on assembly structure and interface geometry measured on the B-rep ([arXiv 2605.28579](https://arxiv.org/abs/2605.28579)); RealCADBench has part and assembly tracks from industrial design intents ([arXiv 2609.03773](https://arxiv.org/abs/2609.03773)); and CADEngBench adds parametric behaviour, functional editing, matched linear-static FEA in CalculiX and an assembly-joint track ([arXiv 2608.09296](https://arxiv.org/abs/2608.09296)). All four descriptions were verified against the primary pages.

### Frontier models execute reliably, edit well and generate poorly

On these newer benchmarks, general-purpose models write runnable code and miss the geometry. The figures in this paragraph were checked against the primary pages on 2026-11-13, and several were corrected. On RealCADBench's part track, GPT-5.5 reached an execution rate of 0.93 with a solid IoU of 0.38 (verified). The best solid IoU was **0.45**, from Kimi K3, which executed on only 34% of tasks; among models that executed on more than 80% of tasks the best was 0.43, from Gemini 3.1 Pro Preview (corrected: the report had called 0.43 the best of any model). Solid IoU there is computed only over outputs that executed. On the 25-task assembly study, standalone Claude Opus 4.8 had the second-lowest judge score of eight configurations, 60.2 against 76.3 for GPT-5.5, ahead only of Doubao Seed 2.0 Pro (corrected from "lowest of four models") ([arXiv 2609.03773](https://arxiv.org/html/2609.03773)). On BenchCAD's image-to-code track the best frontier total was 0.397 (Gemini 3.1 Pro with thinking), with Claude Opus 4.7 at 0.38, while the CADEvolve specialist scored 0.60 and the authors' own 2-billion-parameter model fine-tuned on BenchCAD data scored 0.59 to 0.77 (verified against the leaderboard table; the paper's body text quotes 0.318 for the same Gemini entry, an inconsistency in the source). GPT-5.3 showed low recall on chamfer (4 to 9%), revolve (11 to 14%), fillet (0 to 12%) and loft (6 to 24%), against 83 to 84% on extrude (corrected from "near-zero recall"; shell rests on four samples and sweep recall was about 50%), and the authors report models replacing sweeps, lofts and twist-extrudes with plain extrudes ([arXiv 2605.10865](https://arxiv.org/html/2605.10865)). The MUSE claim needs a flag. The first version's text does say the best closed models reach "only about 19–21%" on functionality, manufacturability and assemblability, but its own tables list Claude Opus 4.7, Gemini 3.1 Pro and GPT-5.5 at roughly 37 to 55% on those criteria, and the current v3 drops those criteria altogether. v3 instead reports joint success of 23.6% for Claude Opus 4.7 and 34.9% for GPT-5.5 against execution success of 76 to 77%, and 57.6% joint success for its strongest model at 99% execution ([arXiv 2605.28579](https://arxiv.org/html/2605.28579)). The 19 to 21% figure should not be relied on. Later aggregator leaderboards show much higher numbers for newer models, some with tools, but those pages conflict with the papers and use different subsets and harnesses, so the researchers rate them low-reliability ([Klu.ai](https://klu.ai/benchmarks/benchcad)). The one primary leaderboard that could be read directly, CADGenBench on Hugging Face, does show harnessed agents far above these single-shot numbers by late 2026; see the evaluation section below.

Two patterns matter for product design. First, models understand and edit CAD code far better than they create from images: BenchCAD's edit track scored 0.84 to 0.87 for the three leading models with thinking enabled, against roughly 0.4 for generation (verified against the primary page, [arXiv 2605.10865](https://arxiv.org/abs/2605.10865)). The two numbers use different metrics (a headroom-normalised IoU improvement for edits, a composite total for generation), and one figure caption in the paper says edits trail generation, so the comparison is indicative only. CADEngBench supports the pattern independently: across eight models, editing supplied CAD was substantially easier than generating it, with 4.6 times as many items passing only the edit task as passing only generation (verified against the primary page, [arXiv 2608.09296](https://arxiv.org/abs/2608.09296)). Second, vendor ranking flips by benchmark and by capability. CADEngBench found Gemini ahead on requirement satisfaction and Claude ahead on executability and parametric behaviour, with the leading point estimates not separable from the next-best system under corrected significance tests and generation and editing ranks only weakly associated (verified against the primary page; the models were Gemini 3 Flash and Claude Sonnet 4.5, not the flagship tiers, [arXiv 2608.09296](https://arxiv.org/abs/2608.09296)). No controlled study was found that measures one 2026 frontier model bare, with a render loop, and with kernel tools on the same benchmark; the CADGenBench leaderboard rows discussed below are the nearest thing, and they are uncontrolled.

### Commercial products cluster into code agents, learned generators and assistants

Zoo is the most buildable-on commercial stack: its Zookeeper agent shipped in January 2026 with Design Studio v1.1, and Zoo's MCP server carries no separate fee, with hosted operations billed as metered API usage from the same monthly credit as Zookeeper reasoning time (verified against the primary pages, [Zoo research post](https://zoo.dev/research/zookeeper), [Zoo API pricing](https://zoo.dev/api-pricing)). An October 2026 third-party check lists tiers at $0, $20 and $99 per month (secondary, [llms.blog](https://www.llms.blog/posts/best-ai-cad-tools)); Zoo's own September 2025 billing post confirms the free tier and the $20 Plus tier, and the $99 figure could not be checked because the live plan table loads client-side. Adam raised a $4.1M seed and is moving from consumer text-to-3D toward a professional CAD copilot (secondary, [Apollo Technical](https://www.apollotechnical.com/ai-cad-tools/)). Backflip raised a $30M Series A for scan-to-CAD ([TechCrunch](https://techcrunch.com/2024/12/19/backed-by-a16z-and-nea-backflip-raises-30m-series-a-to-turn-text-into-ai-generated-designs/)). Spectral Labs' SGS-1 outputs B-rep STEP from an image or mesh but cannot create assemblies in one shot (vendor-reported, [Spectral Labs](https://www.spectrallabs.ai/research/SGS-1)). Mach9 raised $34M after pivoting to AI CAD software ([TechCrunch](https://techcrunch.com/2026/10/21/mach9-raises-34m-after-pivoting-to-ai-cad-software/)).

Incumbent assistants are mostly question-answering and command automation. Autodesk's "neural CAD" is the distinct bet on generative B-rep, and Autodesk itself says it cannot yet guarantee precision and pairs it with deterministic parametric engines ([DEVELOP3D](https://develop3d.com/cad/autodesks-ai-blueprint-for-cad/)). Much comparative coverage is vendor-authored, and no independent accuracy benchmark of any commercial tool on a public benchmark was found.

The open-source route is a coding-agent plugin. earthtojake/text-to-cad is an MIT-licensed set of skills for Claude Code and other agents in which the agent writes build123d and exports STEP, STL, 3MF and GLB ([GitHub](https://github.com/earthtojake/text-to-cad)). Its star count is cited as about 9,300 in one blog and about 22,000 in a community survey, and sources also disagree on how many skills it bundles.

## Simulation agents run 88 to 100% of the time and are physically right 0 to 34%

### Gmsh plus CalculiX is the pragmatic default

For clean B-rep, Gmsh is the default headless mesher: it installs from PyPI, embeds the OpenCASCADE kernel and imports STEP shapes directly ([PyPI](https://pypi.org/project/gmsh/4.15.0/), [PyVista CAD-to-FEA example](https://cad.pyvista.org/examples/05_workflows/cad_to_fea_tet_mesh.html)). fTetWild is the robustness fallback for dirty triangle input; its authors report it always succeeds on the Thingi10k set ([arXiv 1908.03581](https://arxiv.org/abs/1908.03581v2)), at roughly 38 seconds per model against 2 seconds for TetGen in one comparison ([arXiv 2109.14434](https://arxiv.org/pdf/2109.14434)). Those results are for triangle meshes, and no sourced failure rates for Gmsh on real STEP files were found.

CalculiX 2.23 (October 2025) is still current in November 2026 (reported, [calculix.de](https://calculix.de)). The researchers recommend it as the default solver for linear static, modal, buckling and thermal analysis because its input is a single declarative text deck in the Abaqus dialect, it is one binary, and existing pipelines already target it: FeaGPT translates structured JSON specifications into CalculiX input ([arXiv 2510.21993](https://arxiv.org/pdf/2510.21993.pdf)) and FreeCAD's FEM workbench uses it by default ([FreeCAD wiki](https://wiki.freecad.org/FEM_CalculiX)). The Python wrappers are narrow: pygccx is limited to 3D solid elements and pycalculix to 2D ([pygccx](https://github.com/QiangF/pygccx), [pycalculix](https://pypi.org/project/pycalculix/1.1.2)). FEniCSx/DOLFINx suits custom physics and adjoints, but its API still changes every release ([DOLFINx release notes](https://docs.fenicsproject.org/dolfinx/main/python/release_notes.html)). Code_Aster, with more than 4,600 verification cases by its own description ([OSArch wiki](https://wiki.osarch.org/index.php/Code_Aster)), is the researchers' suggested second backend for fatigue, shells and advanced contact; that positioning is unverified background. One news article reports the OpenRadioss explicit-dynamics project was shut down in October 2026 with a community fork set up ([It's FOSS](https://itsfoss.com/news/siemens-openradioss-fork.md)); this is a single source and needs confirmation.

### Face identity must be rebuilt at every file boundary

No reliable carrier exists for face names across CAD, mesh and solver. STEP face names are vendor-dependent (secondary, [STEP guide](https://takuto-na.github.io/step-standards-explained/docs/persistent-ids)), Gmsh users report STEP labels failing to appear ([Gmsh issue 2437](https://gitlab.onelab.info/gmsh/gmsh/-/issues/2437)), and Gmsh's CalculiX export has several set-writing quirks, including surface groups that emit 2D elements CalculiX does not need ([Roland Smith's write-up](https://rsmith.home.xs4all.nl/engineering/fea-based-on-step-geometry-using-gmsh-and-calculix.html)). Passing an in-memory CadQuery shape to Gmsh is fragile too: one report traced an OCCT exception to a pip-installed stack and fixed it with a clean conda install ([CadQuery issue 1556](https://www.github.com/CadQuery/cadquery/issues/1556)). The working pattern, shown by CadQuery's assembly-mesh-plugin, matches tagged faces to Gmsh surfaces in one Python process ([PyPI](https://pypi.org/project/assembly-mesh-plugin/)). The researchers infer three design rules from this: keep selections as executable geometric queries re-evaluated on each rebuild, write the CalculiX deck with your own thin writer from the Gmsh API, and emit a "selection audit" (face count, area, centroid, highlight image) before every solve. No source demonstrated face names surviving build123d to STEP to Gmsh end to end.

### CFD automation is harder, and commercial APIs mean sales calls

OpenFOAM remains the open CFD default in two diverging lines: ESI's v2606 (June 2026), which adds first GPU offloading and Python bindings, and the Foundation's v14 (July 2026) (reported, [OpenFOAM v2606](https://www.openfoam.com/news/main-news/openfoam-v2606), [openfoam.org v14](https://openfoam.org/14)). The researchers flag the split itself as an automation hazard because models mix the two dialects (unverified background). For mechanisms, MuJoCo 3.14 and Project Chrono 10.0.0 are the actively released options (reported, [MuJoCo](https://en.wikipedia.org/wiki/MuJoCo), [Project Chrono](https://en.wikipedia.org/wiki/Project_Chrono)).

Among commercial services, only Luminary Cloud publishes usable API pricing, at $5 per credit with SDK access ([Luminary pricing](https://www.luminarycloud.com/pricing/)). SimScale ties dedicated API support to its quote-only Enterprise plan ([SimScale pricing](https://www.simscale.com/product/pricing/)). PyAnsys libraries are free clients that still require a licensed solver behind them, and Ansys terms require a licence for each user accessing the program "directly or indirectly" ([Ansys product codes](https://ansys.com/content/dam/legal/ansys-product-codes-january-2025.pdf)). The researchers infer that an agent serving many users through one commercial seat likely breaches standard terms, which open solvers avoid.

### Executability is nearly solved; correctness is not

Published simulation agents report high run rates on author-chosen tasks. Foam-Agent 2.0 claims 88.2% success on 110 OpenFOAM cases with Claude 3.5 Sonnet, against 55.5% for MetaOpenFOAM, where success means the case ran (verified against the primary page, [arXiv 2509.18178](https://arxiv.org/html/2509.18178v2)). MooseAgent's current version reports a 93% average over nine cases run five times each: 100% on seven of them, including linear elasticity and steady heat conduction, 80% on thermo-mechanical coupling and 60% on plasticity (corrected: the 40% thermo-mechanical figure the report quoted comes from the April 2025 first version and was superseded in the October 2025 revision, [arXiv 2504.08621](https://arxiv.org/abs/2504.08621)). Independent benchmarks that demand physical accuracy tell a different story: the best model reached only **34% on FoamBench and 14% on CFDCodeBench** (verified against the primary page, [CFDLLMBench](https://arxiv.org/abs/2509.20374v2)). On FEABench the best agent produced executable API calls 88% of the time, yet only one problem passed the strict cut of a valid answer within 10% of the target, and the authors attribute that pass to an exported solver default, not a correct solution (verified against the primary page; "no problem fully solved" is a fair reading but is the report's wording, [arXiv 2504.06260](https://arxiv.org/abs/2504.06260v1)). A MOOSE case study of one chemical-vapour-deposition model names the failure "false summit": a converged, plausible-looking simulation that implements the wrong physics, including an omitted reaction term that the model repeatedly rationalised as valid (verified against the abstract, [arXiv 2606.21841](https://arxiv.org/abs/2606.21841)). A separate benchmark reports that after execution-only repair, 39 to 40% of 220 MOOSE cases ran but still solved the wrong physics (verified against the primary page, [arXiv 2605.09360](https://arxiv.org/html/2605.09360)).

The design consensus is to constrain the model. FeaGPT uses structured JSON specifications, and a 2026 FEniCS system confines the model to mapping the prompt to a structured spec and generating meshing code only when geometry is outside a deterministic catalogue ([arXiv 2606.10928](https://arxiv.org/html/2606.10928)). The researchers recommend the same split: Claude emits a schema-validated analysis spec with loads bound to face selectors, deterministic code writes the deck and runs the checks, and Claude interprets only structured results. They also recommend fixing one unit system in code, because CalculiX is unitless and unit mix-ups produce no solver warning (unverified background).

### Verification should be deterministic code, and surrogates can wait

Sourced verification practice is modest but clear. One trade article proposes a global force-balance imbalance of at most 1% of applied load and mesh convergence across at least three refinement levels (secondary, [Robotics & Automation News](https://roboticsandautomationnews.com/2026/05/06/how-fea-software-improves-structural-design-accuracy/101216/)). Richardson extrapolation assumes monotonic convergence and gives no reliable error estimate otherwise ([SAE 2005-01-1774](https://saemobilus.sae.org/papers/solution-verification-linked-model-validation-reliability-confidence-2005-01-1774)). NAFEMS publishes standard linear-elastic benchmarks with reference solutions ([ESRD guide](https://www.esrd.com/resource-library/product/standard-nafems-benchmarks-linear-elastic-tests)). The researchers' fuller check suite (mass from mesh versus CAD volume to catch unit errors, reaction sums, a three-level convergence study, a closed-form hand calculation, and NAFEMS regression in continuous integration) is informed judgement, and no sourced example of such a harness for CalculiX was found.

AI surrogates are production-relevant mainly for automotive and aerospace external aerodynamics, where large datasets exist: NVIDIA's PhysicsNeMo ships a DoMINO recipe trained on DrivAerML ([PhysicsNeMo docs](https://docs.nvidia.com/physicsnemo/26.05/physicsnemo/examples/cfd/external_aerodynamics/domino/README.html)), and Transolver-3 scales to meshes above 160 million cells ([arXiv 2602.04940](https://arxiv.org/html/2602.04940v1)). General physics foundation models such as Poseidon are limited mostly to simple Cartesian domains ([NeurIPS 2024](https://proceedings.neurips.cc/paper_files/paper/2024/hash/84e1b1ec17bb11c57234e96433022a9a-Abstract.html)). The researchers judge a surrogate not worth building for part-level linear FEA that already solves in seconds to minutes; no sourced cost-benefit study was found. Open topology optimisation is research-grade, with FEniTop on FEniCSx the most maintainable route ([FEniTop paper](https://link.springer.com/article/10.1007/s00158-024-03818-7)).

## Printing automates today; milling needs a CAM kernel, a simulator and a human

### Slicers are the easiest manufacturing output

Fused-filament printing is the one manufacturing path that is headless-ready. OrcaSlicer documents a command-line mode for automation and continuous integration ([OrcaSlicer wiki](https://www.orcaslicer.com/wiki/cli/cli_mode)), and PrusaSlicer advertises its CLI for batch slicing ([Prusa](https://www.prusa3d.com/p/prusaslicer/index.md)). The `augura` package computes overhangs, wall thickness and contact footprint analytically on the B-rep for build123d and STEP inputs ([PyPI](https://pypi.org/project/augura/)), though at version 0.1 it is young. Slicer time and material estimates double as a cost proxy (inference). PrusaSlicer and its descendants are AGPL-3.0, and enforcement is active: Bambu Lab faces allegations of AGPL violations ([Tom's Hardware](https://www.tomshardware.com/3d-printing/open-source-non-profit-claims-bambu-lab-violated-license-move-follows-cease-and-desist-demand-on-orcaslicer-fork-that-restored-cloud-printing-features-without-using-bambu-connect)). Run slicers unmodified as subprocesses.

### FreeCAD CAM is the only open milling backbone, with caveats

FreeCAD's CAM workbench is the only open option found that combines STEP import, a Python job and operation API, Python post-processors and headless execution through `FreeCADCmd` ([CAM scripting](https://wiki.freecad.org/CAM_scripting), [Headless FreeCAD](https://wiki.freecad.org/Headless_FreeCAD)). Three caveats apply. The wiki still describes the workbench as in early development; not all modules load automatically in headless mode; and the CAM API changed incompatibly between 1.1 and 1.2-dev ([freecad-mcp listing](https://glama.ai/mcp/servers/blwfish/freecad-mcp)). Whether CAM operations compute fully without the GUI was not confirmed and needs a hands-on test. OpenCAMLib is a pip-installable 3-axis drop-cutter kernel that leaves linking, stock handling and posting to the user ([PyPI](https://pypi.org/project/opencamlib/)). The commercial fallback is the Fusion Automation API. Autodesk's announcement says it includes the Fusion Scripting API and "thus covers the entire design and manufacturing process", and it names milling automation (Toolpath's integration for programming parts) and industrial 3D printing as example applications, at 3.0 Flex tokens per processing hour (verified against the primary page, [APS blog](https://aps.autodesk.com/blog/design-automation-api-fusion-now-generally-available)). The page does not use the words "subtractive CAM", list supported strategies, or say whether simulation results are returned, so CAM coverage is implied by the scripting API and the milling example and still needs a hands-on check.

For sheet metal, FreeCAD's SheetMetal add-on unfolds and exports DXF, but its unattended command is hidden behind an "Engineering Mode" preference and the workbench warns of topological-naming breakage ([SheetMetal UnattendedUnfold](https://wiki.freecad.org/SheetMetal_UnattendedUnfold), [SheetMetal Workbench](https://wiki.freecad.org/SheetMetal_Workbench)). The researchers suggest starting with parts that are already flat, projecting a planar face to DXF. No sources on nesting tools were retrieved.

### AI CAM products are plug-ins, not building blocks

Commercial AI CAM arrives as plug-ins inside incumbent systems, scoped to 3-axis and 3+2 prismatic milling. CloudNC's CAM Assist claims up to 80% programming time saved ([Modern Machine Shop](https://www.mmsonline.com/products/cloudnc-ai-assisted-cam-software-accelerates-cnc-programming)), and Hexagon's ProPlanAI claims 75% ([Hexagon](https://hexagon.com/company/newsroom/press-releases/2024/hexagons-new-ai-powered-automation-slashes-machine-tool-programming-time-by-75-per-cent)). Both figures are vendor-reported with no independent benchmark. Toolpath has raised $20M in total plus a strategic Autodesk investment ([Autodesk News](https://adsknews.autodesk.com/en/news/strategic-investment-toolpath/)). No public API documentation was found for any of the three. All write into a host CAM system for a programmer to review, which is the human-in-the-loop pattern a new agent should copy (inference).

### The literature says the model should never emit final G-code

Research shows models can write simple G-code but fail on numeric grounding and long programs. The ARKNESS authors state that models "routinely hallucinate numeric values and provide no provenance" for process parameters ([arXiv 2506.13026](https://arxiv.org/abs/2506.13026v1)). One study found ChatGPT deleted a pocket-milling operation amounting to about 31% of a program and removed tool-length compensation and safe-return commands (secondary; primary not retrieved, [ownyourai.com](https://ownyourai.com/?p=41267)). GLLM validates generated G-code with syntax checks and a Hausdorff-distance comparison to the intended shape ([alphaXiv 2501.17584](https://alphaxiv.org/overview/2501.17584v1)), and a 2026 paper argues simulation alone does not prove G-code safety ([arXiv 2605.10568](https://arxiv.org/pdf/2605.10568)). Machining feature recognition is near-saturated on synthetic data, at 99.29% accuracy for AAGNet on MFCAD++ ([arXiv 2504.07134](https://arxiv.org/pdf/2504.07134)), with transfer to real parts the open problem. No benchmark of model-generated toolpaths with collision metrics was found.

Verification tooling is the weakest open link. CAMotics simulates 3-axis G-code and exports the cut workpiece, but no headless mode is documented ([LinuxLinks](https://www.linuxlinks.com/camotics-3-axis-cnc-gcode-simulator/)), and no open Python library for stock simulation with holder and fixture collision checking surfaced. The researchers suggest a simple in-house heightmap simulator for 3-axis work; that is a design recommendation, not a sourced fact.

### Quoting and manufacturability checks must be built in-house

No self-serve instant-quote or DFM API from Xometry, Protolabs, Fictiv or SendCutSend was confirmed; a third-party blog's claim of a Xometry developer portal could not be verified ([third-party blog](https://www.topbubbleindex.com/blog/xometry-design-resources)). Absence of search hits does not prove partner APIs do not exist. PartPacket offers a hosted MCP server comparing live print estimates, capped at 20 quote requests per IP per day ([PartPacket](https://mcpservers.org/servers/partpacket-com-docs)). Open manufacturability tooling is fragmentary: the author of Analysis Situs notes a thickness field alone is insufficient for automatic DFM ([Analysis Situs blog](https://quaoar.su/blog/category/dfm-analysis)). The researchers recommend in-house rules over the B-rep (machine envelope, internal corner radius against tool radius, depth ratios, thin walls, setup count, undercuts) and cost estimates derived from the pipeline's own cycle-time and slicer outputs.

## Kernel checks beat renders, and the checker must not be the generator

### Code execution with a few bounded tools is the convergent design

Anthropic's guidance and every leading 2026 CAD harness point the same way: the agent writes a build123d or CadQuery script in a sandbox, and a small set of high-level commands return structured, size-bounded results. Anthropic reports that presenting tools as code cut one workflow from 150,000 to 2,000 tokens ([Anthropic, code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)) and advises building a few tools for high-impact workflows over wrapping every endpoint, with actionable errors and eval-first development ([Anthropic, writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)). The agentcad project applies this to CAD: every command returns JSON, failures carry an error kind, responses are bounded to about 2,000 tokens, and every build is versioned ([agentcad](https://github.com/jdilla1277/agentcad)). build123d-mcp exposes execute, measure, render, compare and validate against a persistent session and recommends one feature at a time ([build123d-mcp](https://github.com/pzfreo/build123d-mcp)). Fine-grained "create box, add fillet" tools are absent from the leading harnesses. No comparative measurement of the two styles on the same tasks was found, so the preference rests on general guidance and ecosystem convergence.

Role-split multi-agent teams (planner, CAD engineer, geometry reviewer, structural reviewer) are common in papers, but none of the numbers found isolate the benefit of the role split from the benefit of tool-grounded feedback. The better-evidenced principle is separating generation from verification. Anthropic found generators "reliably skew positive when grading their own work" and that a separate evaluator is far easier to tune toward scepticism; it also found the harness costly (a three-agent run at $200 against a solo run at $9) and that components became unnecessary as models improved ([Anthropic, harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)). The DFM-Redesign pipeline shows the same small-verified-step pattern for CAD, applying one manufacturability edit at a time and verifying each, though its authors say the improvement is not yet quantified ([arXiv 2609.05559](https://arxiv.org/html/2609.05559v1)).

### Renders catch gross errors; dimensions need the kernel

The strongest evidence on feedback type comes from CADTests, which expresses a prompt's design specification as executable B-rep tests (topology counts, bounding boxes, volumes, containment), with 5,937 tests over 200 parts ([arXiv 2605.07807](https://arxiv.org/html/2605.07807v1)). In a study of 125 generations labelled by two expert annotators, the tests' pass/fail verdicts matched the human consensus with an accuracy of **0.938 against 0.474 for a language-model-judge metric**, and putting the tests and geometric log queries into the generation loop raised Claude Sonnet 4.6's pass rate on abstract prompts from 0.715 with execution feedback alone to 0.810. Both figures were verified against the paper's tables. The annotators agreed with each other only moderately (Cohen's kappa of 0.54), and the paper also found that adding four-view renders to the loop did not improve performance. Vision models show view-dependent failures: in Blueprint2CAD, Claude's accuracy at matching a drawing to a render fell from 0.98 on right-side views to 0.46 on top views without dimensions (verified against the primary page, [arXiv 2611.02433](https://arxiv.org/html/2611.02433)). CADSmith's authors conclude visual feedback cannot resolve dimensional errors ([arXiv 2603.26512](https://arxiv.org/pdf/2603.26512)), and AssemCAD argues renders give limited guidance for assemblies ([arXiv 2607.05123](https://arxiv.org/html/2607.05123v1)). Renders still help: CADCodeVerify's render-and-question loop cut point-cloud distance by 7.30% with GPT-4 (verified against the primary page, [arXiv 2410.05340](https://arxiv.org/html/2410.05340v2)), and practitioners report iterating on rotated renders "works quite well" (anecdotal, [HN thread](https://hn.nuxt.dev/item/47183039)).

The researchers' resulting hierarchy, which is inference, runs from kernel validity, to spec-derived geometric assertions, to solver results, to multi-view renders for gross-shape sanity, to a human view. Writing the geometric tests from the requirement before writing the CAD keeps the generator from grading itself.

### Requirements belong in a machine-checkable spec

Two requirements practices have evidence behind them. Asking the user for missing dimensions before generating cut mean Chamfer distance by 79.9% in ProCAD (secondary, unverified, [torno survey](https://github.com/luisg0nc/torno/issues/42)). And agentcad holds the spec as a `spec.json` checked against the STEP file, keeping "spec check passed", "geometry valid" and "human approved" as three distinct states ([agentcad](https://github.com/jdilla1277/agentcad)). Work on generating SysML v2 with language models reports that outputs are unreliable without parsers and deterministic validation ([ScienceDirect](https://www.sciencedirect.com/science/article/pii/S0920548926000656)), so the researchers suggest a lighter schema: each requirement has an ID mapped to at least one executable check. Domain knowledge is shipped as skills and helper libraries in the leading harnesses, as text-to-cad does with separate skill folders for CAD, FEA with CalculiX and manufacturing checks ([text-to-cad](https://github.com/earthtojake/text-to-cad)). No sources were found on unit-handling libraries in engineering agents, material databases, standard-part libraries or retrieval over engineering handbooks.

### Evaluation has moved from shape similarity to functional checks

Chamfer distance and IoU are the legacy metrics and correlate poorly with whether a part is right. CADGenBench instead gates on validity, then scores a weighted mean of shape similarity, interface match and topology match over 81 real mechanical parts, 49 generated from engineering drawings and 32 edited from an existing STEP solid (verified against the primary page, [dataset card](https://huggingface.co/datasets/HuggingAI4Engineering/cadgenbench-data); code at [cadgenbench](https://github.com/huggingface/cadgenbench)). The third-party mirror figure the report first relied on, a leading aggregate of 0.451 with all generation scores below 0.4 ([benchmarklist.com](https://benchmarklist.com/benchmarks/cadgenbench/)), matches the leaderboard as it stood in June 2026 and is badly out of date (corrected). The primary [results file](https://huggingface.co/datasets/HuggingAI4Engineering/cadgenbench-submissions), read on 2026-11-13, shows maintainer-validated entries at **0.851** (Godela, generation 0.90, editing 0.77) and 0.830 (build123d-mcp with Claude Opus 5.5, generation 0.87), and several unvalidated entries between 0.84 and 0.87. Single-shot build123d baselines from the maintainers and the data provider stayed between 0.17 and 0.45 through August 2026, and no validated baseline for the newest models is listed, so the jump from about 0.45 to above 0.8 cannot be split between harness and model from this data. The two harness-gain figures both check out against the results file and are not in conflict: 0.360 to 0.457 is GPT-5.5 without and with build123d-mcp, and 0.6268 to 0.6391 is Claude Opus 5 with the baseline prompt (an unvalidated row) and with build123d-mcp ([build123d-mcp](https://github.com/pzfreo/build123d-mcp)). Read together they suggest the harness added about 0.10 for the older model and about 0.01 for the newer one, which is consistent with Anthropic's observation that harness components matter less as models improve. All of these are self-submitted results on 81 public inputs. EngDesign evaluates 101 tasks across nine engineering domains with simulation-based scripts and three runs per task (verified against the primary page, [arXiv 2509.16204](https://arxiv.org/html/2509.16204v2)). No benchmark covers the whole requirements-to-manufacturing chain, and none has physical build-and-test ground truth.

## The open chain stops at CAD-to-FEA, so build outward from single parts

### What nobody has shown

No project found has publicly demonstrated a full CAD-to-simulation-to-CAM loop run by an agent; absence in search is not proof of absence. The integration frontier is CAD-to-FEA. Hephaestus-CCX, the closest reusable reference, pairs 50 engineering briefs (20 single-part, 30 multi-part) with CalculiX evaluation kits and typed pass/fail checkers covering structural, vibration, buckling, thermal, dimensional, geometric and material-compliance requirements. The agent writes CadQuery and exports an assembled STEP file, and the harness meshes it with Gmsh, runs CalculiX and grades the solver output. The agents tested were Codex with GPT-5.5 and Claude Code with Claude Opus 4.7. Beyond the zero strict passes in 400 first attempts, one FEA-feedback round added a single strict pass across another 400 revised submissions, and the best configuration met about 20% of typed requirements on first attempt. Persistence helps: the longest GPT-5.5 run, with blueprint planning, 21-view render review and increasingly detailed FEA feedback, lifted mean requirement pass from 38.8% to 60.5% with 9 of 50 strict passes, at an average of **68 minutes per item**. Several of those nine passes came from simplifying geometry or from exposing the metadata names the checker expected, not from structural redesign. The authors ran no repeated trials and report no confidence intervals. Every figure in this paragraph was verified against the primary page; the paper's title is "Self-Improving CAD Generation Agents with Finite Element Analysis as Feedback", and Hephaestus-CCX is the benchmark it releases ([arXiv 2605.17448](https://arxiv.org/html/2605.17448v2)).

Commercial agents cover one or two stages inside a vendor's cloud. SimScale launched an Engineering AI Agent inside Onshape that proposes a setup, runs the physics and explains results (vendor-reported, [SimScale press](https://www.simscale.com/press/simscale-launches-engineering-ai-agent-for-onshape/)). Synera, which raised a $40M Series B in April 2026, orchestrates more than 80 incumbent tools and advises building deterministic workflow automation first with agents layered on top ([SiliconANGLE](https://siliconangle.com/2026/04/14/german-startup-synera-lands-40-million-automate-engineering-workflows-ai-agents/), [Synera blog](https://www.synera.io/news/ai-agent-orchestration-engineering-use-cases)). Funded "AI engineer" startups cluster in knowledge search (Leo AI), documentation (Foundation EGI) and orchestration (Synera, Navier). The researchers read that clustering as evidence that autonomous geometry with validated physics remains commercially unsolved. No independent evaluation of any commercial agent was found.

### Risks ranked by evidence

The dominant, well-evidenced risk is silent wrongness. It appears as converged simulations with wrong physics, as valid-looking multi-part outputs with intersecting solids (a community reproduction of Hephaestus-CCX reports "36 valid solids but 38 intersecting pairs", [Reify issue #37](https://github.com/QiuYi111/Reify/issues/37)), and as tools that fail to report failures (9 of 16 unreported in one six-agent test; secondary, [torno survey](https://github.com/luisg0nc/torno/issues/42)). User trust is correspondingly low: an IoT Analytics survey of 120 manufacturers found only 17% trust AI-generated simulation inputs and auto-meshing, and 61% say transparency would raise trust ([IoT Analytics](https://iot-analytics.com/the-ai-trust-gap-in-design-and-engineering-software/)). A self-selected survey of 402 US engineers found 52.4% default to a hand sanity calculation ([Omni Calculator](https://www.omnicalculator.com/reports/ai-adoption-in-engineering)).

The remaining risks are structural. Assemblies are much harder than parts across benchmarks. Tolerances, GD&T and drawings are barely addressed in the literature. Code-CAD output loses the native feature tree when imported into SolidWorks, Fusion or Onshape. build123d and FreeCAD CAM both break APIs between releases, so model training data lags the libraries. No sources were found on legal liability or professional-engineer sign-off for AI-generated designs.

Licensing is manageable for an internal tool and needs review for anything shipped. Gmsh is GPL-2.0-or-later with a linking exception ([SPDX](https://spdx.org/licenses/Gmsh-exception.html)), OCCT is LGPL-2.1 with its own exception ([OCCT exception](https://licenses.nuget.org/OCCT-exception-1.0)), and the Hephaestus-CCX asset table lists CadQuery as Apache-2.0, CalculiX as GPL version 2 or later, and Gmsh as GPL version 2 or later with its linking exception (verified against the primary page, [arXiv 2605.17448](https://arxiv.org/html/2605.17448v2)). The researchers' general reasoning, which is not legal advice and not drawn from a cited source, is that running unmodified GPL tools as subprocesses behind a hosted service is generally considered compatible with closed orchestration code, while shipping container images or on-premises builds counts as distribution and triggers source obligations. Licences for CalculiX, OpenFOAM, FreeCAD and build123d were not confirmed from primary sources.

### Recommended open stack

The table below is the researchers' synthesis. Component facts are cited above; the choices are inference.

| Layer | Primary choice | Fallback or later addition | Main caveat |
|---|---|---|---|
| Geometry | build123d on OCCT 8.0.1, pinned, with current docs in context | CadQuery (most benchmark coverage); FreeCAD when a feature tree, assemblies or drawings are needed; Zoo or Onshape for geometry OCCT cannot build | Pre-1.0 API churn; no persistent face naming |
| Agent surface | Claude writing scripts in a sandbox; a thin CLI or 6 to 10 tools returning bounded JSON (build, inspect, render, check-spec, diff, validate, fea-run, dfm-check, export) | MCP wrapper for a persistent kernel session | Preference rests on guidance and convergence, not a controlled test |
| Verification | Spec-derived B-rep assertions; selection audit; independent reviewer subagent with fresh context; hooks that block completion on failing checks | Multi-view render tiles with scale bars as a secondary signal | Wall-thickness and interference checks have no accuracy evaluation |
| Meshing | Gmsh Python API in-process, quadratic tetrahedra | fTetWild on tessellated geometry when Gmsh fails | Loses CAD face association on fallback |
| Structural FEA | CalculiX with an in-house deck writer | Code_Aster for shells, fatigue, contact; FEniCSx for optimisation | Units are unchecked by the solver |
| CFD and dynamics | Defer; OpenFOAM (pin one line) | Luminary Cloud for pay-per-use; Chrono or MuJoCo for mechanisms | Correctness rates are lowest here |
| Printing | OrcaSlicer or PrusaSlicer CLI, unmodified | augura or custom printability checks | AGPL; keep at arm's length |
| Milling | FreeCAD CAM via `FreeCADCmd`, pinned version, templated operations | Fusion Automation API | Headless CAM unconfirmed; no open collision simulator |
| Rendering and viewer | PyVista off-screen (EGL or OSMesa, no X server) ([PyVista docs](https://docs.pyvista.org/extras/docker)) | Web viewer with version compare and surface-pinned comments, as in agentcad | — |
| Packaging | One pinned conda image for geometry, Gmsh, CalculiX and PyVista; separate images for FreeCAD and for FEniCSx/OpenFOAM | Everything baked into the image for restricted networks | Separation is inferred from one pip-versus-conda failure report |

### Build order for one to three people

No source publishes a tested roadmap, and no practitioner account of where a real sequence stalled was found. The sequence below is the researchers' synthesis from what demonstrably works, what struggles, and what is unbenchmarked.

| Milestone | Scope | Evaluation problems |
|---|---|---|
| M0 | Pinned container image, artefact store, run manifest with tool versions and inputs | Reproducible rebuild of a reference bracket |
| M1 | Single-part code-CAD: skills, geometric assertion library, multi-view renders, web viewer, STEP/STL/3MF export, clarifying-question step | Dimensioned brackets, plates, enclosures against assertion suites; CADGenBench or BenchCAD subsets for regression |
| M2 | Query-based face selections with audit; in-process Gmsh; own CalculiX deck writer; linear static only; typed checkers; hand-calc cross-check; automatic report | Cantilever bracket (beam theory), plate with hole (handbook stress concentration), thin-wall pressure vessel (hoop stress) |
| M3 | Parameter sweeps and optimisation over a human-approved parametric model, with a standard optimiser in the inner loop; add modal and buckling | Drone arm stiffness, mass and first mode; a Hephaestus-CCX subset |
| M4 | 3D-print path: slicer CLI, printability checks, time and material report | Snap-fit enclosure, fixtures |
| M5 | Flat-part DXF for laser and waterjet services; 2.5D milling through a CAM kernel with templates, stock simulation and mandatory human sign-off | Fixture plates, simple pocketed housings |
| M6 | Thermal and CFD; assemblies with contact | Heat sink, gearbox housing |

Closed-form problems come first because they give an oracle that is independent of the agent, which directly tests for false-summit behaviour. Tracking strict pass, mean requirement pass, wall time and cost per solved case over at least three runs per task keeps progress comparable to Hephaestus-CCX and EngDesign. Human sign-off belongs at spec freeze, at concept selection, before release of anything load-bearing, and before any spend or machine run. Agent FEA should be labelled screening-grade until a hand calculation agrees.

## Conclusion

The research changes the shape of the build problem. Geometry generation, solver invocation and slicing are commodity capabilities reachable with a coding agent and a sandbox, and they will keep improving with each model release without effort from the team. What does not come for free is an oracle: a set of executable checks, tied to a written spec and owned by code the agent cannot edit, that says whether a part is right. That harness is the durable asset, and Anthropic's own experience suggests building it so components can be removed and re-tested as models improve. The eval suite is the product's backbone for the same reason.

Three unknowns deserve a hands-on spike before committing to the plan, because the research could not settle them: whether FreeCAD CAM computes toolpaths fully headless, whether face selections survive the build123d-to-Gmsh handoff reliably in one process, and how the current Claude model performs on a Hephaestus-CCX subset inside this specific harness. The least crowded territory with clear demand is tolerances, drawings and assembly mates, where public research is thin; that is a reason to stay away from it in a first version and a reason to watch it closely afterwards. The verification pass of 2026-11-13 re-read the figures the argument leans on. The Hephaestus-CCX results, the FEABench and CFDLLMBench numbers and the CADTests agreement figures all held, so the central conclusion stands. One supporting claim weakened: single-shot generation scores near 0.4 are no longer the ceiling, because harnessed agents on newer models now exceed 0.8 on CADGenBench's 81 drawing-to-CAD and editing tasks. That narrows the generation gap on single parts with a reference shape; it does not touch the gap on physics-checked requirements, where the only public numbers remain those of Hephaestus-CCX. Still unverified are Zoo's current plan allowances, the current Fusion Automation API rate and its CAM coverage, and every claim cited to hosts outside the five that were re-checked.
