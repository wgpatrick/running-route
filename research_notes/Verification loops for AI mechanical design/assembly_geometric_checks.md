## 1. Assembly representation: build123d, CadQuery, FreeCAD Assembly, Onshape, STEP/XCAF

### Takeaway
For a scripted agent loop, build123d (label/anytree Compound tree + one-shot Joints) and CadQuery (`cq.Assembly` + a numerical constraint solver) are the two workable headless representations; neither stores persistent mates, and neither detects over/under-constraint for you. FreeCAD's integrated Assembly workbench is only partly scriptable headless and its solver is approximate and non-deterministic, and Onshape has no interference endpoint in its REST API.

### Cited Findings

**build123d (0.13.0, Sept 2026)**
- An assembly is a `Compound` tree built by assigning `parent`/`children`; `Shape` subclasses anytree's `NodeMixin` (`parent`, `children`, `leaves`, `descendants`, ...). Labels are plain strings and need not be unique. `location` is relative to the parent; `global_location` gives the accumulated world placement. `show_topology()` prints the tree. — [build123d docs/assemblies.rst](https://github.com/gumyr/build123d/blob/dev/docs/assemblies.rst)
- `assembly.volume` returns only the top-level value, while `sum(p.volume for p in assembly.solids())` walks nested compounds (docs example: 1 vs 3), a trap for mass roll-up. — [build123d docs/assemblies.rst](https://github.com/gumyr/build123d/blob/dev/docs/assemblies.rst)
- `copy.copy()` shares the underlying OCCT TShape; in the docs' 100-screw example deep copies took about 5 s and a ~52 MB STEP, shallow copies about 0.25 s and ~550 KB. — [build123d docs/assemblies.rst](https://github.com/gumyr/build123d/blob/dev/docs/assemblies.rst)
- Joint types and valid pairings: `RigidJoint`↔`RigidJoint`; `RevoluteJoint`→`RigidJoint`; `LinearJoint`→`RigidJoint` or `RevoluteJoint`; `CylindricalJoint`→`RigidJoint`; `BallJoint`→`RigidJoint`. Joints "always work in pairs". — [build123d docs/joints.rst](https://github.com/gumyr/build123d/blob/dev/docs/joints.rst)
- Connecting joints "only does a one time re-position of a part and does not bind them in any way"; values outside declared limits "will raise an exception"; joint labels must be unique within a part. The joints page does not describe any constraint solver or closed kinematic loops. — [build123d docs/joints.rst](https://github.com/gumyr/build123d/blob/dev/docs/joints.rst)
- `export_step` writes labels and colors by walking the tree into an XCAF document (search summary). — [build123d exporters3d source (readthedocs)](https://build123d.readthedocs.io/en/latest/_modules/exporters3d.html)

**CadQuery (2.8.0, June 2026)**
- Constraint kinds: `Point`, `Axis` (default param 180° = mate), `Plane` (= Point + Axis), `PointInPlane`, `PointOnLine`, `Fixed`, `FixedPoint`, `FixedAxis`, `FixedRotation`. `solve()` sets up an optimisation: "The solver varies the location of the assembly's children and attempts to minimize the sum of all cost functions." — [cadquery doc/assy.rst](https://github.com/CadQuery/cadquery/blob/master/doc/assy.rst)
- Documented caveats: "In an underconstrained system the solver may not move an object if it does not contribute to the cost function"; initial locations influence which solution is reached and are overwritten by the solution. — [cadquery doc/assy.rst](https://github.com/CadQuery/cadquery/blob/master/doc/assy.rst)
- Current master implements the solver with CasADi + IPOPT (`import casadi as ca`, `"ipopt"`, `tol` 1e-14, 6 DOF per entity), not nlopt. `solve()` locks the first entity if nothing is fixed and raises `ValueError` for "At least one constraint required" / "At least two entities need to be constrained". — [cadquery/occ_impl/solver.py](https://github.com/CadQuery/cadquery/blob/master/cadquery/occ_impl/solver.py), [cadquery/assembly.py](https://github.com/CadQuery/cadquery/blob/master/cadquery/assembly.py)
- `Assembly` exposes `toCompound()`, `traverse()`, `shapes()`, `addSubshape()`, `export()`, and `importStep` / `load` for STEP, XML and XBF. No interference or collision method is present in the class's method list. — [cadquery/assembly.py](https://github.com/CadQuery/cadquery/blob/master/cadquery/assembly.py)
- Reported robustness problems (search summaries): Discussion #1981 reports vertex positions "computed inaccurately by the constraints solver"; PR #1890 proposes an initializer that walks the constraint graph to give the solver a starting point; issue #1911 reports a segfault on `import cadquery` in an environment listing nlopt 2.9.1. — [cadquery issue #1911](https://github.com/CadQuery/cadquery/issues/1911), [cadquery assembly docs](https://cadquery.readthedocs.io/en/latest/assy.html)
- STEP export of an assembly keeps colors but, per the CadQuery docs, not the names set on each part unless the `addSubshape`/metadata path is used (search summary). — [CadQuery import/export docs](https://cadquery.readthedocs.io/en/stable/importexport.html)
- CadQuery `union()` can silently produce a disconnected compound under face-only contact; AssemCAD built a `SafeUnion` cascade (plain union → glue → micro-extension) with a post-condition of exactly one solid to counter it. — [AssemCAD, arXiv 2607.05123](https://arxiv.org/abs/2607.05123)

**FreeCAD integrated Assembly workbench (1.0 Nov 2024 → 1.1, 24 March 2026; 1.1.4 current)**
- FreeCAD 1.1 was released 24 March 2026 (search summary); a dev build 26.3.0RC1 dated 2026-10-08 exists and 1.1.4 is referenced as a release. — [FreeCAD 1.1 release notes](https://wiki.freecad.org/Release_notes_1.1), [FreeCAD issue #33557](https://github.com/FreeCAD/FreeCAD/issues/33557)
- Headless test under `freecadcmd` on FreeCAD 1.0.2: `Assembly::AssemblyObject` can be created with `GuiUp: 0` and exposes `solve()`/`undoSolve()`; `JointObject.Joint(obj, index)` takes an integer index into `JointObject.JointTypes` (a type-name string raises `TypeError`); grounding via `GroundedJoint` works. But `isPartConnected` stayed False and driving a joint moved nothing, because the solver wants `Reference1`/`Reference2` in a path format the author could not find documented. The author retracted an earlier "fully scriptable headlessly" claim. — [constraint-kit issue #28](https://github.com/jajmangold/constraint-kit/issues/28)
- Open issue (Oct 2026): "the solver is not deterministic when multiple solutions exist" — joint/placement values change between recomputes without visible motion, producing spurious diffs; reported on 26.3.0RC1 and 1.1.4; no maintainer diagnosis yet. — [FreeCAD issue #33557](https://github.com/FreeCAD/FreeCAD/issues/33557)
- Earlier reports (search summaries): 1.0 RC2 solver "bogs down" in larger assemblies with repeated "Solve failed: iterNo > iterMax"; a performance issue describes one core pegged for seconds to minutes on simple assemblies; a grounded part's Placement moving unexpectedly. — [FreeCAD issue #17734](https://github.com/FreeCAD/FreeCAD/issues/17734), [FreeCAD issue #16771](https://github.com/FreeCAD/FreeCAD/issues/16771), [FreeCAD issue #32650](https://github.com/FreeCAD/FreeCAD/issues/32650)
- Joint set (search summary of a code wiki): Fixed, Revolute, Cylindrical, Slider, Ball, plus RackPinion, Screw, Gears, Belt; solver is OndselSolver (MbD-based) and needs at least one grounded object. — [DeepWiki FreeCAD assembly objects](https://deepwiki.com/FreeCAD/FreeCAD/3.7.1-assembly-objects-and-joints)

**Onshape**
- Forum answers (c. 2022, search summary) say there is no REST endpoint for interference checking; the workaround is a FeatureScript custom feature called through the API, which only works inside a Part Studio. Mate details can be read via the assembly feature-list endpoint. — [Onshape forum: API endpoint for interference](https://forum.onshape.com/discussion/19704/is-there-an-api-endpoint-for-checking-interference-between-two-parts), [Onshape forum: mate info from API](https://forum.onshape.com/discussion/11460/is-there-a-way-to-get-specific-information-of-a-mate-from-api)
- A community Onshape MCP server advertises interference checking but implements it with bounding boxes, i.e. an approximation (search summary). — [hedless/onshape-mcp](https://github.com/hedless/onshape-mcp)

**Research-system representations worth copying**
- AssemCAD represents an assembly as typed parts + geometry-backed *ports* (12 port types such as `BOLT_SEAT`, `SHAFT`, `BORE`) + executable *mates*; `.mate("part:port", ...)` checks type compatibility via a matrix and dispatches to one of seven mate functions, each a closed-form rigid transform (no numeric solver); output is a standard `cq.Assembly` and STEP with hierarchy. — [AssemCAD, arXiv 2607.05123](https://arxiv.org/abs/2607.05123)
- ArtiCAD predicts assembly relations at design time through a "Connector" that defines attachment points and joint parameters before geometry is generated, to bypass weak LLM spatial reasoning; its kinematic-tree formulation "cannot represent closed kinematic chains" (four-bar, scissor linkages). — [ArtiCAD, arXiv 2604.10992](https://arxiv.org/abs/2604.10992)

### Inferences
- Deterministic, closed-form mate transforms (build123d joints, AssemCAD ports, ArtiCAD connectors) are a better fit for a generate→verify→revise loop than iterative solvers (CadQuery IPOPT, FreeCAD Ondsel), because results are reproducible and failures are attributable to one mate. The cost is no closed loops and no automatic DOF analysis.
- Because build123d joints and CadQuery solved locations do not persist as constraints, the verifier must re-derive "is this mate still satisfied" from final geometry (axis coincidence, face coplanarity, distance) rather than trusting declared joints.
- build123d's non-unique labels mean the agent's own code should enforce unique part names (or paths) before any verifier reports pairs by name.

### Gaps
- Assembly4 and A2plus: no source found on their 2026 status or headless behaviour; the search returned nothing specific.
- STEP AP242 assembly structure (product/NAUO, validation properties, PMI) and OCCT XDE/XCAF details (`XCAFDoc_ShapeTool`, instance vs prototype labels): no primary source could be opened; build123d/CadQuery behaviour above is from search summaries only.
- FreeCAD 1.1's Assembly-specific changes and whether the reference-path format is now documented: not confirmed (release notes page not fetchable).
- Onshape API rate limits and any 2025-2026 change to interference support: not found; forum evidence is about four years old.
- I could not confirm the current GitHub release tags; versions above are from PyPI.

## 2. Interference / clash detection

### Takeaway
The consensus recipe in 2026 tools is: bounding-box broad phase → optional mesh/BVH "definitely apart" filter → exact B-rep `BRepAlgoAPI_Common` volume for surviving pairs, with a small volume noise floor (0.001 mm³ recurs) and an explicit allow-list for intended overlaps. Exact Common is usually milliseconds to about a second per pair, but exact minimum distance (`BRepExtrema_DistShapeShape`) scales roughly quadratically in face count and can take minutes on gears or lofts.

### Cited Findings

**build123d built-ins**
- `Compound.do_children_intersect(include_parent=False, tolerance=1e-5)` compares assembly leaf parts at their global locations: for every pair it first intersects bounding-box solids, then does an exact `intersect()` and sums the common solid volume. It returns `(bool, (shape_a, shape_b), volume)` for the **first** pair whose common volume exceeds the tolerance, then stops. — [build123d topology/composite.py](https://github.com/gumyr/build123d/blob/dev/src/build123d/topology/composite.py)
- The official joints tutorial has a step titled "Check that the components in the assembly don't intersect" (search summary). — [build123d assemblies docs](https://build123d.readthedocs.io/en/latest/assemblies.html)
- `Shape` also provides `intersect`, `touch(other, tolerance=1e-6)` (returns boundary-contact vertices/edges/faces), `distance`, `distance_to`, `distance_to_with_closest_points`, `closest_points`, `distances`, `is_valid`, `is_manifold`, `fix`, `bounding_box`, `matrix_of_inertia`, `static_moments`, `compute_mass`, `radius_of_gyration`. `Compound.touch` distributes over elements in global coordinates; only Solid and Face elements produce contacts. — [build123d topology/shape_core.py](https://github.com/gumyr/build123d/blob/dev/src/build123d/topology/shape_core.py), [build123d topology/composite.py](https://github.com/gumyr/build123d/blob/dev/src/build123d/topology/composite.py)

**Measured OCCT behaviour (fit-check prototype, Nov 2026)**
- `BRepAlgoAPI_Common` overlap volume: correct on valid solids (within 4e-8 relative error of closed forms); typically 1–50 ms on analytic parts, ~1 s for a freeform B-spline loft, 0.7–1.3 s for a 2019-face gear in a ring. — [laminarityai/cad issue #92](https://github.com/laminarityai/cad/issues/92)
- `BRepExtrema_DistShapeShape` minimum distance: correct to about 2e-7 mm, but time is roughly quadratic in face count. Examples: analytic rail clip ~5 ms; plate with 8×8 holes (204 faces) 209 ms; plate with 32×32 holes (3084 faces) 35.7 s; stacked spur gears 0.5 mm apart 166 s. — [laminarityai/cad issue #92](https://github.com/laminarityai/cad/issues/92)
- Converting analytic geometry to NURBS cost 6–8× more for distance and 30–80× more for Common; peak RSS ~250 MB typical, 612 MB for the gear; one self-shifted B-spline loft was OOM-killed at 2 GB. — [laminarityai/cad issue #92](https://github.com/laminarityai/cad/issues/92)
- Pitfalls found: (a) for a part fully nested inside another, distance returned 2.0 mm, not 0 — containment must come from the overlap test; (b) a self-overlapping input made Common return 100 instead of 200; (c) an invalid solid made Common return 177,035 instead of 0; (d) face-only/open-shell inputs give zero volume; (e) a non-zero fuzzy value hid overlaps of 1e-5 to 1e-6 mm; (f) `SetMultiThread(true)` on distance was up to 3.6× slower, and `SetRunParallel` on Common gave no gain; (g) a custom face-pair prefilter was slower (365 s vs 166 s). — [laminarityai/cad issue #92](https://github.com/laminarityai/cad/issues/92)
- Recommended order from that prototype: validate (`BRepCheck_Analyzer`, max shape tolerance ≤ 1e-3 mm, no stray faces/wires) → Common with fuzzy 0 → distance only if no overlap; classify overlap above 0.001 mm³ as interference, distance below 1e-7 mm with zero overlap as touching, and report `unknown` (never pass) on any precondition failure, timeout (60 s) or OOM. — [laminarityai/cad issue #92](https://github.com/laminarityai/cad/issues/92)
- `BRepExtrema_ShapeProximity` is a BVH tool that reuses face triangulations; its result is approximate to the mesh deflection, shapes must already be triangulated (users report crashes otherwise), and forum advice is to pass tolerance 0 for overlap-only tests; `BRepExtrema_DistShapeShape` is described as an older class with no acceleration structure (search summary of OCCT forum threads). — [OCCT ShapeProximity reference](https://dev.opencascade.org/doc/occt-6.9.1/refman/html/class_b_rep_extrema___shape_proximity.html), [OCCT forum: intersect without BRepAlgoAPI_Common](https://occt3d.com/dev/content/find-out-if-2-shapes-intersect-without-brepalgoapicommon/index.html)

**Whole-assembly pipeline at scale (text-to-cad `cad model interference`, release 0.11.9, 2026)**
- Pipeline: bounding-box filter → mesh each candidate pair at 0.05 mm or finer and run `BRepExtrema_ShapeProximity`; if no triangle is within the deflection and no shell sits inside the other solid, the pair is "apart" and no Boolean runs → all other pairs get an exact kernel overlap volume, fewest-faces first, across up to four processes, with a guard that kills orphaned workers. — [earthtojake/text-to-cad PR #823](https://github.com/earthtojake/text-to-cad/pull/823)
- Performance on a humanoid robot model, four cores: cold run about 10 minutes for 1,802 box-overlapping pairs (985 ruled apart by the mesh test, 746 measured exactly); repeat run 0.16 s from cache; 16 s after one part edit; eleven mechanism states (12 poses, 21,946 pairs) about 5 minutes. Eight pairs (lofted panels on liners) took two to three minutes each. — [earthtojake/text-to-cad PR #823](https://github.com/earthtojake/text-to-cad/pull/823)
- Results are cached by the two parts' geometry keys plus relative placement, so an edit re-measures only pairs containing the edited part; a cache-key bug (an edited plain attribute reusing a stale result) produced "drives six degrees off their bolt holes". — [earthtojake/text-to-cad PR #823](https://github.com/earthtojake/text-to-cad/pull/823)
- Lessons recorded there: a first check based on point sampling "could not see a plate through a thin skin", so the verdict moved to exact kernel overlap volume; pair loops, pruning and parallelism written ad hoc per agent "were wrong", motivating a shared tool. — [earthtojake/text-to-cad PR #823](https://github.com/earthtojake/text-to-cad/pull/823)
- Limits: pairs past five minutes or a whole check past twenty minutes are stopped and reported unmeasured; the mesh "apart" rule is not proven for all shapes. — [earthtojake/text-to-cad PR #823](https://github.com/earthtojake/text-to-cad/pull/823)

**Intended contact vs real clash**
- text-to-cad: noise floor 0.001 mm³; the only allow-list is `--fit A B`, naming a pair meant to share volume and listing it separately. — [earthtojake/text-to-cad PR #823](https://github.com/earthtojake/text-to-cad/pull/823)
- build123d-mcp `clearance()` returns a four-way status — `apart`, `touching`, `containing`, `interpenetrating` — plus `containment` (`a_in_b`/`b_in_a`/`neither`), `intersection_volume`, and each part's volume outside the other; guidance is that mating parts should be `touching` or `apart`. The older `interference` tool (bool, volume, bounds) was removed in v0.3.47 (June 2026) in favour of `clearance()`. — [build123d-mcp llms.md](https://github.com/pzfreo/build123d-mcp/blob/main/llms.md), [build123d-mcp CHANGELOG](https://github.com/pzfreo/build123d-mcp/blob/main/CHANGELOG.md)
- A FreeCAD-style MCP `check_interference` tool returns pairs above `tolerance_mm3` with common volume, overlap centre and size, and treats zero-volume face contact as not interference (search summary). — [cad_mcp check_interference](https://glama.ai/mcp/servers/abhinavpathak9873/cad_mcp/tools/check_interference)
- bd_warehouse fasteners default to `simple=True` ("simplify by not creating thread"), so a screw is a plain cylinder at nominal size unless modelled threads are requested. — [bd_warehouse fastener.py](https://github.com/gumyr/bd_warehouse/blob/main/src/bd_warehouse/fastener.py)

**Mesh-based fast paths**
- trimesh `CollisionManager` wraps `fcl`: `add_object(name, mesh, transform)`, `set_transform`, `in_collision_internal(return_names, return_data)` for all-pairs checks, `in_collision_single`, `in_collision_other`, and `min_distance_*` queries; contact data exposes names, point, normal and depth. — [trimesh collision.py](https://github.com/mikedh/trimesh/blob/main/trimesh/collision.py)
- python-fcl managers support one-to-many and internal many-to-many checks; collision queries can return all contact pairs while distance queries return only the single closest pair (search summary). — [python-fcl on PyPI](https://pypi.org/project/python-fcl/)
- Coal (the renamed hpp-fcl, "An extension of the Flexible Collision Library") is at 3.0.3 and manifold3d ("Library for geometric robustness") at 3.5.5 on PyPI. — [pypi coal](https://pypi.org/pypi/coal/json), [pypi manifold3d](https://pypi.org/pypi/manifold3d/json)

### Inferences
- `do_children_intersect` is not sufficient as an agent verifier on its own: it returns only the first offending pair, has no allow-list, does not separate containment from interpenetration, and its 1e-5 volume tolerance is far below the 0.001 mm³ floor other tools settled on. It is a reasonable building block; a wrapper should enumerate all pairs.
- For 50–500 parts the pair count after a bounding-box filter is what matters (the humanoid gave 1,802 box-overlapping pairs). A cold exact pass is minutes, not seconds, so per-pair caching keyed on geometry hash + relative transform is the single most important performance feature for an edit loop.
- Threads and press fits need a declared-intent mechanism rather than geometric guessing: keep fasteners as simple (unthreaded) cylinders, declare expected-overlap pairs (press fits, modelled threads, gear mesh at nominal), and report those separately with their volume so a wrong-sized "intended" overlap is still visible.
- A mesh collision library is useful as a broad/middle phase or for swept-motion sampling, but the point-sampling failure reported above and the deflection-bounded accuracy of ShapeProximity argue for exact B-rep volume as the final verdict.
- The verifier should have a three-valued result (pass / fail / unmeasured); both the laminarity and text-to-cad designs insist that an unmeasured pair is never reported as a pass.

### Gaps
- No benchmark found comparing `BOPAlgo_ArgumentAnalyzer` / `BRepAlgoAPI_Check` (self-interference and argument validity) with the tools above.
- No direct measurement found of trimesh/FCL, Coal or Manifold on tessellated CAD assemblies of 50–500 parts, and no confirmation that trimesh supports a Coal backend.
- FreeCAD's own clash tooling (scripted) was not researched to a citable source.
- `BRepExtrema_ShapeProximity` exact-distance behaviour in OCCT 7.7+/7.9 was not confirmed from current docs (the reference found is the 6.9 page).

## 3. Clearance, fit, fastener/hole, connectivity and mass checks

### Takeaway
Minimum-distance, contact, mass and bounding-box primitives exist in build123d/OCCT, and bd_warehouse/cq_warehouse encode clearance and tap drill tables by fit class, but there is no off-the-shelf open library that checks fastener-to-hole compatibility, hole-pattern coaxiality, thread engagement or "no floating parts". Research systems (AssemCAD, MUSE) implement these as typed-interface checks on B-rep evidence, and that is the pattern to copy.

### Cited Findings
- build123d measurement primitives usable for these checks: `distance_to_with_closest_points`, `closest_points`, `touch`, `bounding_box`, `center`, `compute_mass`, `matrix_of_inertia`, `static_moments`. — [build123d topology/shape_core.py](https://github.com/gumyr/build123d/blob/dev/src/build123d/topology/shape_core.py)
- bd_warehouse fasteners carry `clearance_drill_sizes`, `clearance_hole_diameters(fit)` with `fit: Literal["Close","Normal","Loose"]`, `tap_drill_sizes` / `tap_hole_diameters` keyed by material class "Soft (Aluminum, Brass, & Plastics) or Hard (Steel, Stainless, & Iron)", `countersink_profile(fit)`, `min_hole_depth(counter_sunk)`, and a `hole_locations` list recorded on the fastener when holes are cut. `ClearanceHole(fastener, fit="Normal", counter_sunk=True, captive_nut=False, ...)` is the hole object; captive nuts are limited to hex, domed-cap and square nuts. — [bd_warehouse fastener.py](https://github.com/gumyr/bd_warehouse/blob/main/src/bd_warehouse/fastener.py)
- cq_warehouse provides the equivalent `clearanceHole`, `tapHole`, `threadedHole` Workplane methods for CadQuery (search summary). — [cq_warehouse fastener docs](https://cq-warehouse.readthedocs.io/en/latest/fastener.html)
- AssemCAD port-geometry verification uses OCCT `BRepClass3d_SolidClassifier`: *bore check* samples axial points along the declared bore direction (must be OUT) and radial ring points (at least one IN); *shaft check* samples axial points at quarter and three-quarter length (IN) and a radial point outside the diameter (OUT); *flat-face check* searches for a face with collinear normal passing within 1 mm of the port origin. Failures produce "structured error messages with natural-language hints designed for LLM-consumable repair feedback". — [AssemCAD, arXiv 2607.05123](https://arxiv.org/abs/2607.05123)
- AssemCAD's deterministic verification pipeline checks "interface validity, clash consistency, graph connectivity, degree-of-freedom constraints, and engineering-rule compliance", and wraps cq_warehouse screws, nuts and washers with 5, 3 and 3 ports (thread ports, head seats, bearing faces). — [AssemCAD, arXiv 2607.05123](https://arxiv.org/abs/2607.05123)
- AssemCAD's failure catalogue maps LLM failure modes to gates: "phantom bore" (a `Workplane("XZ")` sign trap makes `.cut()` miss the solid, so an axle transfixes an undrilled arm) → port-geometry check; "disjoint compound" → SafeUnion; "all-coincident parts" (zero-offset mates to the same port) → overlap validator; "port-frame surprise" → strict x-direction; "semantic mis-selection" (wrong factory for a role) → visual reflection. — [AssemCAD, arXiv 2607.05123](https://arxiv.org/abs/2607.05123)
- MUSE's Structure and Interface Evaluation recovers a "Physical Assembly Graph" directly from the generated STEP (solids as nodes, physical interfaces as typed edges) and scores component correspondence (Node F1), connectivity (Edge F1), interface type (Type F1), graph edit distance and interface clearance. Clearance is computed per paired side face from face centroids and outward normals (single-side clearance), summed into total fitting clearance per cross-section direction; pairs are pruned by solid and face bounding-box distance first. — [MUSE, arXiv 2605.28579](https://arxiv.org/abs/2605.28579)
- MUSE matches generated solids to reference component names by normalized geometric descriptors and a global assignment with unmatched options and an ambiguity margin — relevant to BOM/completeness checks when part names are unreliable. — [MUSE, arXiv 2605.28579](https://arxiv.org/abs/2605.28579)
- CADGenBench "Interface match" asks "Would it bolt up to the same fixture?": each mating feature is an authored keep-out or keep-in sub-volume and the candidate is scored on how well its material matches that region; it is weighted 0.4 in the generation CAD Score (0.4 shape + 0.4 interface + 0.2 topology) and one misplaced mating group can drive the interface score to 0.00 while shape similarity stays 0.89. — [cadgenbench docs/metrics.md](https://github.com/huggingface/cadgenbench/blob/main/docs/metrics.md)
- CADEngBench-A verifies a predicted joint by turning the joint frame into a URDF joint executed in PyBullet, with scripted probes for allowed motion, stability and blocked motion; origin must match within 1% of body size. — [CADEngBench, arXiv 2608.09296](https://arxiv.org/abs/2608.09296)
- build123d-mcp `measure` returns volume, area, mass (with density or a material preset), centre of mass, inertia tensor, topology counts, bounding box and a face inventory by type; agent guidance is to run it after every Boolean because "a failed cut leaves the face and edge counts unchanged". — [build123d-mcp llms.md](https://github.com/pzfreo/build123d-mcp/blob/main/llms.md)
- Amagine3D (Apache-2.0) is described as committing a candidate version only if it passes checks that include interference, plate fit and connectivity (third-party research note, not verified against the code). — [torno issue #42](https://github.com/luisg0nc/torno/issues/42)

### Inferences
- A contact graph can be built from primitives already available: for each box-adjacent pair, classify as overlapping / touching (`touch` non-empty or distance < 1e-7 mm) / apart; nodes not reachable from a grounded part are floating. Fastened joints should count as connections only when the fastener touches or threads into both members.
- Fastener checks are best done on declared metadata, not reverse-engineered geometry: because bd_warehouse records hole locations and fit class at creation, a verifier can compare the fastener axis with each hole axis (coaxiality), the hole diameter with the table for the chosen fit, the tapped depth with required engagement, and the head with counterbore diameter/depth. AssemCAD's port typing is the same idea generalised.
- Keep-in/keep-out sub-volumes (CADGenBench) are a simple, robust way to express envelope, tool-access and mating-interface requirements: Boolean the part with the region and compare volume fractions.
- Mass roll-up needs per-part density metadata and must iterate leaf solids, given the build123d top-level `volume` trap noted in section 1.

### Gaps
- ISO 286 fit classes (H7/g6 etc.), ISO 273 clearance-hole series, thread-engagement rules and tool/driver clearance tables: no open Python library implementing these as a checker was found, and no primary source for the standards' values was fetched; treat any numbers as needing a separate standards lookup.
- No open tool was found that checks coaxiality of mating hole patterns across two parts or wrench/driver access automatically.
- MUSE's exact clearance thresholds and its interface-type catalogue beyond rectangular mortise-and-tenon were not extracted.

## 4. Tolerance analysis (stack-up)

### Takeaway
Open-source tolerance tooling is limited to small 1D stack-up libraries (dimstack, stackcore, Tol Ninja); nothing open derives the dimension chain from 3D CAD geometry the way commercial 3DCS/CETOL-class tools do. No 2024-2026 paper on LLM-driven tolerance allocation was found.

### Cited Findings
- dimstack (v0.9.0, May 2026): "Python library for 1D statistical tolerancing analysis and design"; API builds `ds.Dim(nom=..., tol=ds.tol.Bilateral.symmetric(...)/unequal(...), name, desc)` items with optional process distributions (`ds.dist.Normal`, `.assume_normal_dist(3)`). Its examples show worst-case, closed, RSS and six-sigma analyses; Monte Carlo was not confirmed. — [dimstack README](https://github.com/phcreery/dimstack), [pypi dimstack](https://pypi.org/pypi/dimstack/json)
- stackcore (v0.3.3, July 2025): "A lightweight Python package for mechanical tolerance stack-up analysis" with a Monte Carlo engine and a numba-parallel variant (search summary). — [pypi stackcore](https://pypi.org/project/stackcore/)
- Tol Ninja: a Monte Carlo stack-up application with a Tkinter GUI handling 1D and coaxial/radial chains, built on NumPy/SciPy/Matplotlib; an application rather than an importable library (search summary). — [slehmann1/Tol-Ninja](https://github.com/slehmann1/Tol-Ninja)
- Method background (search summary of an academic chapter): the linearized vector-loop method does analysis and allocation quickly and suits design iteration; Monte Carlo is random-sampling based; a second-order method was reported as comparable to Monte Carlo with 10^6 samples. — [IntechOpen chapter on tolerance analysis](https://intechopen.com/chapters/52413)
- Commercial tools (search summaries, low confidence): 3DCS Variation Analyst is described by a reseller page as Monte Carlo at its core with added sensitivity/optimisation; an academic paper notes early CETOL versions used vector loops. One blog claims CETOL is 1D/2D only, which conflicts with other descriptions and was discounted. — [3DCS reseller page](https://www.ki-syndikat.de/tools/3dcs-variation-analyst/), [CETOL tech paper](https://www.academia.edu/3644100/CETOL_MSM_Tech_Paper)
- AssemCAD explicitly scopes tolerance out: "production-ready" means executable, connected, interface-valid and interference-free, "rather than fully optimized for manufacturing processes, materials, or tolerance analysis". — [AssemCAD, arXiv 2607.05123](https://arxiv.org/abs/2607.05123)
- "Done Is Not Correct" grades B-rep measurements against published tolerance bands and lists ISO 2768 general-tolerance classes per feature as future work, not part of its evidence. — [Done Is Not Correct, arXiv 2611.10063](https://arxiv.org/abs/2611.10063)
- A targeted search for LLM/agent tolerance stack-up or allocation papers on arXiv returned only unrelated uses of "tolerance" (wireless benchmarks, fault-tolerant control). — [WirelessBench, arXiv 2603.21251](https://arxiv.org/abs/2603.21251)

### Inferences
- The practical route for an agent today is: have the agent declare each critical gap as an explicit 1D loop (signed contributors with tolerances pulled from the parametric script's variables), evaluate worst-case and RSS with dimstack or a few lines of NumPy, and add Monte Carlo only where distributions or non-linear geometry matter.
- A cheap geometric complement: because the model is parametric code, rebuild the assembly at tolerance extremes (max-material / least-material corners or sampled combinations) and re-run the interference and clearance checks — a brute-force substitute for 3D variation analysis that needs no new tooling.
- LLM tolerance allocation appears to be an open gap in the literature as of November 2026.

### Gaps
- How 3DCS, CETOL 6σ, Sigmetrix and Enventive work internally: no vendor or independent source could be opened; statements above are from search summaries only. No source found on Enventive at all.
- FreeCAD tolerance add-ons and any "OpenTolerance"-style project: nothing found.
- dimstack Monte Carlo support and its documentation: not confirmed.

## 5. Research and benchmarks on LLM-generated assemblies (2024-2026)

### Takeaway
Across 2026 benchmarks, executable code is a poor proxy for a correct assembly: the best model on MUSE runs 99% of designs but only 58% satisfy all checks, and frontier models' raw code preserves assembly structure rarely on AssemBench. Typical failures are missing holes, wrong part placement, wrongly typed or badly fitted interfaces, and silently wrong Booleans.

### Cited Findings
- **MUSE** (arXiv 2605.28579, v3 19 Oct 2026): multi-component B-rep text-to-CAD benchmark scoring executability, geometric validity, structure/interface fidelity (SIE) and functional consistency. Claude Opus 4.7: 76.42% execution, 58.49% geometric validity, 63.77% Node F1, 33.02% Type F1, 23.58% joint success. GPT-5.5: 77.36% execution, 34.91% joint success. GPT-6 Astra: 99.06% execution, 89.62% validity, 89.77% Node F1, 86.08% Edge F1, 74.22% Type F1, 57.55% joint success. — [MUSE, arXiv 2605.28579](https://arxiv.org/abs/2605.28579)
- MUSE on fit: GPT-5.5 had the second-highest Type F1 (48.64%) but the largest clearance MAE (0.4750 mm); MiniMax-M2.7 had the lowest (0.2000 mm), possibly because it generates simpler interfaces. "Correctly typed interfaces may still fit poorly." Most models have median hole-count ratios below 1, i.e. generate fewer holes than the reference. — [MUSE, arXiv 2605.28579](https://arxiv.org/abs/2605.28579)
- MUSE argues VLM judging is unreliable when "interface types and interface clearances are obscured in rendered views", motivating direct B-rep analysis. — [MUSE, arXiv 2605.28579](https://arxiv.org/abs/2605.28579)
- **AssemCAD / AssemBench** (arXiv 2607.05123, July 2026): 120 assemblies (avg 3.38 bodies, 4.52 occurrences, 2.23 joints, 9.43 contacts). Text-to-assembly results (Success Rate / Assembly Preservation Rate): GPT-5.5 79.17 / 66.67; Qwen3.7-Max 78.33 / 39.17; GLM-5.2 76.67 / 40.83; Claude-4.8 85.00 / 0.83; AssemCAD 89.17 / 87.50. APR is judged by an LLM code judge (score ≥ 4 of 5), not by geometry. — [AssemCAD, arXiv 2607.05123](https://arxiv.org/abs/2607.05123)
- AssemCAD argues Chamfer Distance is unreliable for assemblies: a structurally correct assembly can score worse than one missing functionally critical components. — [AssemCAD, arXiv 2607.05123](https://arxiv.org/abs/2607.05123)
- **ArtiCAD** (arXiv 2604.10992, April 2026): four agents (Design, Generation, Assembly, Review); validation in the assembly stage uses a VLM over multi-view renders plus an LLM judge combining observations with bounding-box data to give a structured verdict on placement, interference and motion fidelity; failures go through a cross-stage rollback router. ArtiCAD-Bench has 120 assembly tasks (90 real-world designs: 50 articulated, 40 static). Exports URDF. — [ArtiCAD, arXiv 2604.10992](https://arxiv.org/abs/2604.10992)
- **CADEngBench** (arXiv 2608.09296, Aug 2026): the assembly track has 150 body pairs evaluated by ranked joint retrieval, exact face/edge grounding, joint-frame prediction and kinematic verification, one-shot with no retry. Finding: "Assembly predictions often locate the relevant region but fail to recover the recorded joint or mating entities." — [CADEngBench, arXiv 2608.09296](https://arxiv.org/abs/2608.09296)
- **RealCADBench** (arXiv 2609.03773, Sept 2026): models write FreeCAD Python; the image-based Assembly track's reported slice is RCB-Assm25 (25 tasks); metrics are executability, Solid IoU, Surface IoU and a rubric-based visual judge — no interference metric. Recurring failures: "missing fine structures, loss of part identity, and incorrect assembly placement." — [RealCADBench, arXiv 2609.03773](https://arxiv.org/abs/2609.03773)
- **Done Is Not Correct** (arXiv 2611.10063, 6 Nov 2026): 13 single-part tasks, 122 kernel-measured checks. Single-shot agents claimed completion on 98% of attempts and were silently wrong on 14.1%; a tool-use loop enforcing measure-then-claim cut silent failures to 3.2% and raised claim precision from 64% to 96%, with an ablation attributing the gain "to the claim contract rather than the feedback". Hardening the oracle flipped 18 of 519 verdicts from pass to fail and none the other way. It has no assembly tier; interference checks are planned for v2. — [Done Is Not Correct, arXiv 2611.10063](https://arxiv.org/abs/2611.10063)
- **CADGenBench** (Hugging Face): part-level, but its interface-match metric with keep-in/keep-out sub-volumes is the closest published mechanism for "will it bolt up". — [cadgenbench docs/metrics.md](https://github.com/huggingface/cadgenbench/blob/main/docs/metrics.md)
- **Fusion 360 Gallery Assembly / JoinABLe** (CVPR 2022): assemblies with joints, contact surfaces, holes and assembly graphs, from about 20,000 designs, non-commercial research licence; JoinABLe joint-axis accuracy 0.7953 on the full test set (search summary). — [Fusion360GalleryDataset](https://www.github.com/AutodeskAILab/Fusion360GalleryDataset), [JoinABLe, arXiv 2111.12772](https://arxiv.org/abs/2111.12772)
- Practitioner evidence: in a six-agent test a CadQuery `union()` dropped a part's core (7,065 mm³ vs 10,323 mm³) while the solid still read `valid=True`, `solids=1`; nine of 16 failures went unreported by the tool. — [torno issue #42](https://github.com/luisg0nc/torno/issues/42)
- A public "Engineering Bench" CAD leaderboard describes an assembly rung that no model passes yet, graded with a physics solver and FEA (search summary). — [Engineering Bench leaderboard](https://ravi854-engineering-bench.static.hf.space/index.html)

### Inferences
- Benchmarks split into two evaluation styles: judge-based (AssemCAD APR, ArtiCAD, RealCADBench) and B-rep-measured (MUSE SIE, CADGenBench interface, CADEngBench kinematics). The measured ones consistently expose larger gaps, and MUSE and CADTestBench-style results argue for measured checks as the primary signal with VLM review as a supplement.
- The failure modes that an assembly verifier must catch, ranked by how often they recur across sources: wrong/missing holes and bores ("phantom bore", low hole counts), misplaced or coincident parts, floating/disconnected parts, correct interface type with wrong clearance, and silently wrong Booleans that still yield one valid solid.
- AssemBench assemblies average only about 3.4 bodies, and MUSE/ArtiCAD are similarly small; there is no published evidence about LLM agents on 50–500-part assemblies.
- The "claim contract" result suggests the verifier's value depends on the harness forcing a measurement before a completion claim, not just on making the tool available.

### Gaps
- AutoMate dataset statistics and any 2024-2026 follow-ups (e.g. Mates2Motion) were not retrieved.
- Fusion 360 Gallery joint counts (19,156 joint sets / 32,148 joints) came from an aggregator and were not verified against the paper.
- AssemCAD does not report a geometric interference rate per baseline in the passages extracted; "physical validity" numbers were not located.
- Model names (GPT-6 Astra, Claude Opus 4.7/4.8, Qwen3.7-Max, GLM-5.2) are reported exactly as the papers give them; I did not cross-check them.

## 6. Existing "assembly linter"/DRC-style tools and structuring verifier output for an agent

### Takeaway
There is no established mechanical "DRC" standard, but by late 2026 several agent-facing CAD tools (text-to-cad, build123d-mcp, laminarity's checks, AssemCAD, Amagine3D) converge on the same output shape: named part pairs, a categorical status, overlap volume and location, an explicit "unmeasured" outcome, an allow-list for intended fits, and natural-language repair hints.

### Cited Findings
- text-to-cad `cad model interference`: exit code 0 = clear, 1 = a pair shares volume, 3 = a pair went unmeasured ("an unmeasured pair is never reported as a pass"); findings are `overlapping_parts` entries in `measurements.overlaps` with `between`, `volume_mm3` and every pose where it occurs; unmeasured reasons are `over_time`, `process_lost`, `error`; pair accounting (`pairs.apart`, `.kept`, `.measured`) and a `slowest` list are reported; options are `--pose`, `--fit A B`, `--min-volume`. — [earthtojake/text-to-cad PR #823](https://github.com/earthtojake/text-to-cad/pull/823)
- That tool deliberately "takes the poses it is handed and chooses none itself"; draft options for motion sampling, jobs and time budgets were removed before release so that state selection stays with the caller and limits with the engine. — [earthtojake/text-to-cad PR #823](https://github.com/earthtojake/text-to-cad/pull/823)
- build123d-mcp: pairwise `clearance(a, b)` JSON (`clearance`, `status`, `containment`, `intersection_volume`, `a_volume_outside_b`, `b_volume_outside_a`); guidance to run `clearance` before rendering and to treat renders "as visual confirmation only". Its `verify_spec` tool returns per-requirement `PASS` / `FAIL` / `UNVERIFIED` with `conforms` true only when there are no FAILs and at least one requirement was actually checked; it is experimental and off by default and does not check mates or clearances between parts. — [build123d-mcp llms.md](https://github.com/pzfreo/build123d-mcp/blob/main/llms.md)
- A third-party note reports that build123d-mcp keeps `verify_spec` off by default because a "conforms: true" result "may read to an agent as a stop signal" (search summary). — [torno issue #42](https://github.com/luisg0nc/torno/issues/42)
- laminarity fit check design: checks declare dependencies (`REQUIRES = ("interference",)`), write the overlap result before starting the slow distance computation, run in an isolated job, report summed overlap and minimum clearance per solid pair plus body counts, and return `unknown` with a reason on any precondition failure. — [laminarityai/cad issue #92](https://github.com/laminarityai/cad/issues/92)
- AssemCAD verification reports are traceable to rules: "if a clash is detected between two gears, the report not only identifies the interference volume but also references axiom G-02 (module compatibility)", letting the reader tell a specification error from a geometric inconsistency. — [AssemCAD, arXiv 2607.05123](https://arxiv.org/abs/2607.05123)
- ArtiCAD routes each negative verdict through an error classifier that decides whether the fault is design-level or code-level and rolls back to the corresponding stage rather than regenerating everything. — [ArtiCAD, arXiv 2604.10992](https://arxiv.org/abs/2604.10992)
- Other agent CAD tools with related checks: Shapr3D MCP `detect_clash` (pairwise solid check for assembly/keep-out verification), a `verify_assembly` tool in the cadpilot MCP server, agentcad (`inspect`, `check-spec`, `diff`; build123d-first CLI/MCP), jarvis-onshape-mcp (bounding box, part count and mass diffs after each feature) (search summaries / third-party note). — [Alfredoalv13/shapr3d-mcp](https://github.com/Alfredoalv13/shapr3d-mcp), [cadpilot verify_assembly](https://glama.ai/mcp/servers/LBurny/cadpilot/tools/verify_assembly), [jdilla1277/agentcad](https://github.com/jdilla1277/agentcad), [torno issue #42](https://github.com/luisg0nc/torno/issues/42)
- The same third-party survey (Oct 2026) concluded that no local open tool it found computes clash and deviation numbers against a model in the way its author wanted, and that hook-forced verification loops were not found in other tools. — [torno issue #42](https://github.com/luisg0nc/torno/issues/42)

### Inferences
- A workable finding record, synthesised from the tools above: `check` (rule id), `severity`, `status` (pass / fail / unmeasured), `parts` (unique names or tree paths of both parts), `relation` (apart / touching / containing / interpenetrating), `overlap_volume_mm3`, `min_clearance_mm` with closest points, `location` (bounding box or centroid of the overlap), `pose` (for mechanisms), `declared_intent` (e.g. press fit, threaded, sliding), `rule_reference`, and a short `hint` (e.g. "screw_3 axis is 1.2 mm off hole axis of bracket; shift +X"). Include summary counts of pairs apart / measured / unmeasured.
- The direction of the penetration (closest-point vector or overlap bounding box relative to each part's frame) is what turns a finding into a fix; none of the surveyed tools documents an automatic "suggested fix", so this is a place to add value.
- Checks should be ordered and gated (validity → self-interference → pairwise interference → clearance → interface/fastener rules → connectivity → mass/envelope), since upstream failures (invalid solids, self-overlap) make downstream numbers wrong, per the laminarity pitfalls.
- A "pass" summary should state coverage (how many requirements and pairs were actually measured) to avoid acting as a premature stop signal.

### Gaps
- No tool named or marketed as a general open-source "mechanical DRC/assembly linter" with a published rule schema was found; cad-khana's `assert_no_interference` appeared only in a skill-directory listing and was not verified.
- Amagine3D, cadpilot and Shapr3D MCP check implementations were not inspected.
- No study found measuring which verifier output format (JSON vs prose, with/without hints) gives the best agent repair rate for assemblies.
