## 1. Engines compared for mechanism (gantry / linkage / gearbox) verification

### Takeaway
MuJoCo (now 4.0.x, CPU, `pip install mujoco-core` with only numpy as a dependency) is the pragmatic default for a headless Python motion verifier: it has first-class equality constraints (connect/weld for loop closure, joint-to-joint polynomial coupling for gears/screws/rack-pinion, tendon-to-tendon coupling for belts), a DC-motor actuator model, a programmatic model editor (`MjSpec`), headless rendering and an official web viewer. Project Chrono is the more "mechanical-engineering" engine (true gear/pulley/shaft elements, FEA) but is conda-only; Newton (1.8.0, Apache-2.0) is the fast-moving GPU alternative whose Kamino and new "Steel" solvers target closed-loop mechanisms; the rest are niche for this use.

**MuJoCo (Google DeepMind)**
- Release cadence in 2026: 3.5.0 (12 Feb 2026), 3.6.0 (10 Mar), 3.7.0 (14 Apr), 3.8.0 (24 Apr), 3.9.0 (27 May), 3.10.0 (22 Jun), 3.11.0 (27 Jul), 3.12.0 (20 Aug), 3.13.0 (8 Sep), 3.14.0 (22 Sep), 3.15.0 (5 Oct), 3.16.0 (14 Oct), 3.17.0 (22 Oct), **4.0.0 (6 Nov 2026)**, 4.0.1 (11 Nov 2026). — [MuJoCo changelog](https://github.com/google-deepmind/mujoco/blob/main/doc/changelog.rst)
- 4.0.0 split the Python distribution into `mujoco-core` ("minimal bindings and C library depending only on `numpy`"), `mujoco-studio` (Studio viewer + Filament renderer bindings) and the `mujoco` metapackage; docs call `mujoco-core` "ideal for headless servers and RL training", with `mujoco-core[rendering]` adding glfw/pyopengl for classic OpenGL rendering. — [MuJoCo changelog](https://github.com/google-deepmind/mujoco/blob/main/doc/changelog.rst); [MuJoCo python.rst](https://github.com/google-deepmind/mujoco/blob/main/doc/python.rst)
- 4.0.1 fixed a 4.0.0 regression in the sparse Cholesky factorization that "gave the Newton solver a wrong Hessian factor when the constraint Jacobian is sparse, causing slow convergence, wrong accelerations and divergence" — i.e. pin >= 4.0.1 (or 3.17.0) for constraint-heavy mechanism models. — [MuJoCo changelog](https://github.com/google-deepmind/mujoco/blob/main/doc/changelog.rst)
- Equality constraints available in MJCF: `connect`, `weld`, `joint`, `tendon`, `flex`. `equality/joint` "constrains the position or angle of one joint to be a quartic polynomial of another joint. Only scalar joint types (slide and hinge) can be used", with `polycoef` default `"0 1 0 0 0"` (y−y0 = a0 + a1(x−x0) + …); omitting `joint2` locks the joint to a constant. `equality/tendon` "constrains the length of one tendon to be a quartic polynomial of another tendon". — [MuJoCo XMLreference.rst](https://github.com/google-deepmind/mujoco/blob/main/doc/XMLreference.rst)
- 4.0.0 removed `flexvert` equality constraints; added `speculative` contacts flag (conservative advancement to stop fast convex geoms tunnelling through thin obstacles); added elasto-plasticity for joint and tendon springs and flexes; made RK4 fourth-order accurate for ball/free-joint orientations; changed spatial-tendon `sidesite` wrapping semantics (breaking; affects tendon-routed belt/cable models). — [MuJoCo changelog](https://github.com/google-deepmind/mujoco/blob/main/doc/changelog.rst)
- A `dcmotor` actuator "for modeling DC motors" was added in 3.7.0 (Apr 2026) and redesigned in 3.12.0 so its on-board controller `input` selects any subset of `[pos, vel, ff, voltage]`; it has `motorconst`, `saturation`, `thermal` parameters; a `pid` actuator also exists. — [MuJoCo changelog](https://github.com/google-deepmind/mujoco/blob/main/doc/changelog.rst)
- 3.12.0 defined the MJCF grammar in a single schema file `src/xml/mjcf.schema` from which the parser tables are generated (useful as a machine-readable reference for an LLM authoring MJCF). — [MuJoCo changelog](https://github.com/google-deepmind/mujoco/blob/main/doc/changelog.rst)
- 3.13.0 added `sample/render.cc`, "a headless offscreen rendering sample that saves an image to a PNG", supporting Filament and classic OpenGL backends; 4.0.0 extended it to multi-frame raw RGB24 video recording via `--duration` (and removed `sample/record.cc`). — [MuJoCo changelog](https://github.com/google-deepmind/mujoco/blob/main/doc/changelog.rst)
- 4.0.x ships "MuJoCo Studio" with an official **web viewer** (`mujoco-studio --gfx=web`, `mujoco.studio.launch_web`), the browser client shipped as a `mujoco-studio-wasm` wheel. — [MuJoCo changelog](https://github.com/google-deepmind/mujoco/blob/main/doc/changelog.rst)
- 3.17.0: Python bindings run `step`, `forward`, `reset`, `rollout` etc. with the GIL released (thread-parallel sweeps from Python). 3.5.0 added a Python System Identification toolbox. — [MuJoCo changelog](https://github.com/google-deepmind/mujoco/blob/main/doc/changelog.rst)
- Compiler robustness relevant to generated models: non-positive-definite `fullinertia` and geom-inferred inertias are now bounded by `boundinertia` when positive; `mjWARN_INERTIA` is raised for ill-conditioned inertia; meshes are collided as convex hulls with a `maxhullvert` cap. — [MuJoCo changelog](https://github.com/google-deepmind/mujoco/blob/main/doc/changelog.rst)
- MuJoCo models must be kinematic trees; loops are made by building an open chain and adding equality constraints, which are *soft* constraints enforced by the solver. **[search summary]** — [robolaweb equality overview](https://robolaweb.gitbook.io/robolaweb-docs/basic-concept/equality-overview)
- A practitioner pipeline (text-to-cad) notes "A slide never closes a loop in an MJCF (MuJoCo has no slide equality)": a prismatic loop-closing joint must be re-expressed by closing the loop at the nearest hinge or ball; a hinge closure is written as two `connect`s, a ball as one. — [text-to-cad kinematics.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/cad/references/kinematics.md)
- An arXiv paper on parallel-actuated humanoids in MuJoCo/MJX uses soft equality constraints for four-bar and five-bar linkages and notes that such singularities need explicit handling and that closed chains are often approximated as serial chains in other frameworks. **[search summary]** — [arXiv 2507.00273](https://arxiv.org/html/2507.00273v3)

- For the mechanisms in scope (gantries, linkages, gearboxes), the differentiator is not raw speed but (a) whether the engine has *hard* vs *soft* loop closure and (b) whether transmission elements exist as constraints. MuJoCo's loop closures and couplings are soft (tunable by `solref/solimp`), which is fine for "does it move through full travel" but means constraint violation must itself be a monitored pass/fail metric. Chrono, Exudyn and MBDyn solve constraints at the DAE level and are preferable where reaction forces in an over-constrained loop matter.
- GPU engines (MJWarp, Newton, Genesis, Isaac) add an NVIDIA/driver dependency and weaker determinism guarantees; a single-machine verifier simulating one mechanism for a few seconds gains nothing from them. CPU MuJoCo with the GIL-released `rollout` is enough for parameter sweeps.
- Newton's pace (8 minor releases in ~8 months, many features "experimental") makes it a moving target for a pinned sandbox image; MuJoCo's own cadence (15 releases in 2026, a major-version bump with breaking MJCF/API changes in Nov 2026) also argues for pinning and for generating models via `MjSpec` rather than from remembered XML.

## 2. CAD-to-simulation conversion (build123d / CadQuery → MJCF / URDF)

### Takeaway
As of late 2026 there is an open-source, agent-oriented build123d → MJCF/URDF path: earthtojake/text-to-cad (MIT, ~26k stars) exports mechanisms declared with build123d joints, with exact kernel-derived masses/inertias, joint limits found by sweeping parts to contact, gear/rack/screw couplings as MJCF joint equalities, loop closures as `connect` equalities, CoACD decomposition and a `cad mujoco check` linter. Outside that, converters remain tied to GUI CAD (Onshape, Fusion, SolidWorks, FreeCAD) and build123d/CadQuery have no built-in exporter.

### Cited Findings

**text-to-cad (the closest existing analogue to the team's pipeline)**
- "Design physical products with AI": a plugin of agent skills plus a CAD MCP server; models are Python scripts with build123d; skills cover parts/assemblies, PCBs (KiCad ERC/DRC), manufacturability checks, CalculiX stress checks, drawings, Blender renders, and "Robotics and simulation: … URDF for ROS, SRDF for MoveIt and MJCF for MuJoCo". MIT licence; 26.2k stars, 1,510 commits at time of reading. — [text-to-cad README](https://github.com/earthtojake/text-to-cad)
- Mechanism source of truth is "build123d's `RevoluteJoint`, `LinearJoint`, `CylindricalJoint` and `BallJoint` connected with `connect_to`"; `cad model export <id> robot.xml|.urdf` writes the file and binary STL meshes in metres; `cad.mujoco.spec` returns a `mujoco.MjSpec`. "Frames, limits, masses, inertias and meshes come from the kernel, exactly: the model is the source of truth, and the file is regenerated, never edited." — [text-to-cad robot-simulation SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/SKILL.md)
- Mass properties: materials on parts give density so "each link's mass, centre of mass and inertia tensor are the kernel's, exact"; a part with no material "weighs nothing"; `mass(part, grams)` rescales to a measured weight keeping the geometry's inertia shape; `point_mass(...)` adds lumps the CAD omits (e.g. a motor inside a housing). — [text-to-cad robot-simulation SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/SKILL.md)
- Couplings: `gear_pair`, `rack_and_pinion_pair`, and `screw_pair(assembly, name, joint=pitch)` on a cylindrical joint (pitch = mm per 360°) are exported as "MJCF's `<equality><joint>`, URDF's `<mimic>`". — [text-to-cad robot-simulation SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/SKILL.md); [text-to-cad kinematics.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/cad/references/kinematics.md)
- Closed loops (four-bar, slider-crank): tree joints are connected from ground and the last joint paired by label; "The MJCF closes the loop there with an equality between a site on each body (a hinge two `connect`s, a ball one …); the URDF leaves that joint out and says so." The CAD layer has **no loop solver**: "a loop's pairs are not posed (there is no solver)", so named poses, sequences and `cad model ranges` do not work on loop joints, and "The closing joint's range is not enforced." — [text-to-cad robot-simulation SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/SKILL.md); [text-to-cad kinematics.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/cad/references/kinematics.md)
- Joint-limit transfer from geometry: `cad model ranges <id>` "turns or slides each joint alone until its child link meets its parent and prints each stop", with a default `--clearance` of 0.3 mm counting as touching and a `--step` resolution; also works on STEP (`cad step ranges arm.step --step 0.5 --json`). — [text-to-cad robot-simulation SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/SKILL.md); [text-to-cad cad SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/cad/SKILL.md)
- Division of responsibility: a plain export "holds no chosen collision shape, no joint dynamics and no actuator: each part collides as its own mesh (MuJoCo collides a mesh as its convex hull)". Simulation choices (collision primitives via `fit(s, part, "box")`, `decompose()` via CoACD, friction, armature, damping, `frictionloss`, actuators, excludes) live in a separate Python "MuJoCo function" operating on `MjSpec`. Exports follow published-robot conventions: radians, `meshdir="assets"`, `autolimits`, `implicitfast`, a `visual` class in group 2 that collides with nothing and a `collision` class in group 3, explicit `<inertial>`s, a site per named frame, a key per mechanism state. — [text-to-cad robot-simulation SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/SKILL.md)
- The skill's stated risk model for hand-authored descriptions: "the risks are frame placement, joint-axis semantics, units, mesh scale, inertial data and planning semantics, and a file can pass every check while placing a joint in the wrong spot"; and for generated ones: "Check what the kernel cannot know: that each joint's positive motion is the one intended, and that the collision shapes suit the physics." — [text-to-cad robot-simulation SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/SKILL.md)
- Scope limit: the skill is explicitly "Not … a simulation run"; an MJCF "is opened by the person in MuJoCo Studio"; `cad mujoco check` uses "`mujoco-core` and `mujoco-studio`, about 20 MB, no window system". — [text-to-cad robot-simulation SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/SKILL.md); [text-to-cad mjcf-checks.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/references/mjcf-checks.md)

**Other converters**
- onshape-to-robot handles kinematic loops by breaking the graph into a tree with frames and run-time constraints; a mate named `closing_<something>` marks the closure, and "When using the MuJoCo format, onshape-to-robot will add `<equality>` constraints to enforce the kinematic loop"; passive joints are marked `"actuated": false` in `config.json`. — [onshape-to-robot kinematic_loops.rst](https://github.com/Rhoban/onshape-to-robot/blob/master/docs/source/kinematic_loops.rst)

### Inferences
- The lowest-risk conversion design is the one text-to-cad converged on: (1) CAD model = single source of truth for frames, axes, limits, mass/inertia (from OCCT volume properties × density), meshes; (2) a separate, small Python function for simulation-only choices; (3) generated files are never edited; (4) a linter over the compiled model. A team writing build123d already can either adopt/borrow from text-to-cad (MIT) or reproduce the pattern with `MjSpec` directly (~few hundred lines: walk joints → bodies, `Shape.volume/center/matrix_of_inertia` → `<inertial>`, tessellate → STL in metres, joint ranges, sites).
- MJCF is a better target than URDF for machines: URDF is tree-only (loop joints are dropped), has `mimic` but no general constraints, no tendons, no actuator model; text-to-cad's own exporter loses loop closure in URDF.
- Collision strategy for machines: convex hull of each part is wrong for frames, brackets and anything concave (a gantry carriage would "collide" with the rail it wraps). Options in increasing cost: fitted primitives for rails/extrusions/plates; CoACD with metric threshold for concave parts; or skip physics contact entirely and do clash detection on exact B-rep (see §3).
- Units are the dominant silent failure: build123d works in mm, MuJoCo in m/kg/s; mesh scale and inertia (which scales with length^5 for fixed density) must be converted together; a `scale_suspect`-style check is cheap insurance.

### Gaps
- No standalone, maintained "build123d-to-mujoco" or "cadquery-to-urdf" PyPI package was identified other than text-to-cad's bundled tooling; I did not inspect text-to-cad's exporter source, only its skill docs, so robustness on large assemblies (hundreds of parts, e.g. a full Voron) is unknown.
- fusion2urdf, sw_urdf_exporter, FreeCAD CROSS/RobotCAD, cad_to_urdf, onshape2mjcf and Zoo were not examined this session (no primary pages fetched); nothing found on Zoo offering simulation export.
- dm_control `mjcf` vs `MjSpec` status (deprecation) not verified from a primary source.
- V-HACD vs CoACD quality on machined/printed-part geometry: no comparative data collected.

## 3. What to verify, and whether it needs kinematics or dynamics

### Takeaway
Most "does the mechanism move as intended" checks are kinematic and are best done on exact B-rep geometry (sweep joints, measure interference/clearance, find stops), with the physics engine reserved for what kinematics cannot answer: loop-closure feasibility under soft constraints, actuator force/torque/speed margins under an acceleration profile, gravity sag/holding, friction and binding, and resonance-type questions. A mobility (Grübler–Kutzbach) count is a cheap pre-check but is known to be wrong for exactly the redundantly constrained geometries that gantries use.

### Cited Findings
- Kinematic interference on exact geometry, as implemented in text-to-cad: `cad model interference "$ID" --pose … --pose walk@0.6` "measures every pair of parts at each pose it is given"; pass criterion "no two parts share volume, exactly; a pair it could not measure is not a pass"; guidance: "A pose or a motion shows movement; it does not measure it. A check of the model measures the parts as built, so a part that clears there can still pass through another mid-motion" — i.e. sampled-pose clash checks must be given every state and each sequence "at the times that matter". Helper API: `leaves`, `overlap_volume`, `posed` from `cad.build123d`. — [text-to-cad kinematics.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/cad/references/kinematics.md); [text-to-cad cad SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/cad/SKILL.md)
- Range of motion from geometry: `cad model ranges` sweeps each joint *alone* until its child meets its parent, at a step resolution and 0.3 mm default clearance; cost "follows the parts' surface area and detail, not how many parts there are"; a joint that clears all the way round has no geometric stop and needs the actuator's datasheet travel. It does not sweep loop joints. — [text-to-cad cad SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/cad/SKILL.md); [text-to-cad robot-simulation SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/SKILL.md)
- Machine-checkable model-health codes used before any dynamics (exit status 0/1, `--strict`, `--json`): `compile_failed`, `compile_warning`, `contacts_at_rest` (geoms of two bodies intersect at rest deeper than 0.1 mm; 1 mm for a free body resting on a static geom), `visual_geoms_collide`, `inertia_from_visuals`, `scale_suspect` (moving geometry spans > 50 m or < 5 mm, or a mesh > 100 units after scale — "Millimetres read as metres"), `joint_limits_at_rest`, `defaults_not_recommended` (Euler integrator, pyramidal cone, default `solref 0.02 1`, `solref[0]` < 2×timestep, timestep > 5 ms with contacts), `home_key`, `mass_summary` ("a mass off by a power of ten is a unit or a density; a count off by one is a missing joint or actuator"). The final OK line reports counts of bodies, joints, actuators, collision geoms, meshes, keys: "a robot of seven joints that says 0 joints has its joints in the wrong place". — [text-to-cad mjcf-checks.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/references/mjcf-checks.md)
- Recommended MuJoCo settings in that checklist: `implicitfast` integrator; `elliptic` cone with `impratio` 10 for manipulation; timestep 0.5–2 ms; `solref[0]` 0.004–0.01 and at least twice the timestep. — [text-to-cad mjcf-checks.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/references/mjcf-checks.md)
- Mobility counting limits: "the classical Grübler-Kutzbach formulas for mobility can be wrong for special classes of mechanisms"; the criterion treats all constraints as independent, so redundant (common/virtual) constraints from special geometric arrangements of joint axes make it under-count DOF; a local-dimension (numerical rank) test bounds true mobility. **[search summary]** — [Wampler/Hauenstein/Sommese, Mechanism Mobility](https://bertini.nd.edu:443/LocalDimFinder/Mechanism_Mobility.pdf); [Chebychev–Grübler–Kutzbach criterion, Wikipedia](https://www.wikipedia.org/wiki/Chebychev%E2%80%93Gr%C3%BCbler%E2%80%93Kutzbach_criterion)
- LLM linkage-design work uses exactly this kind of symbolic diagnosis as feedback: in "Language Models Refine Mechanical Linkage Designs Through Symbolic Reflection and Modular Optimisation" (arXiv 2604.27962, Apr 2026), 78.6% of refinement trajectories improved and the diagnosed failure modes were overconstraint (56.3%) and underconstraint (35.6%), each mapped to a corrective action (remove a redundant link / add a loop). **[search summary; figures from secondary review sites]** — [emergentmind listing](https://www.emergentmind.com/papers/2604.27962); [themoonlight review](https://www.themoonlight.io/review/language-models-refine-mechanical-linkage-designs-through-symbolic-reflection-and-modular-optimisation)
- Dynamics observables available for actuator and constraint-load checks: MuJoCo reports joint-space force components separately (actuator, limit, friction loss, equality, armature — fixed in 3.14–3.15 so `force`/`torque` sensors account for them); Newton exposes `qfrc_constraint − qfrc_frictionloss` as "the constraint load on a DOF without its own friction loss"; `actuatorfrcrange` carries the drive's force bound from the CAD `limits(effort=)` but "MJCF has no speed bound". — [MuJoCo changelog](https://github.com/google-deepmind/mujoco/blob/main/doc/changelog.rst); [Newton CHANGELOG](https://github.com/newton-physics/newton/blob/main/CHANGELOG.md); [text-to-cad robot-simulation SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/SKILL.md)
- Belt compliance matters for gantry accuracy: a Lagrangian CoreXY model from HKU (validated experimentally, for contour-error estimation) includes inertia, belt stiffness and friction; a 2024 AUT Journal paper models CoreXY belt-pulley dynamics with four rolling/slipping states, stating belt stretch and tension are essential for accuracy; arXiv 2505.19311 models a belt-driven FFF gantry as a spring-mass-damper with belt-stiffness terms. **[search summary]** — [HKU IRIS paper](https://www.iris.mech.hku.hk/_files/ugd/80702a_108ba3af77434288b2a18a1100baf8a0.pdf); [AUT J. Model. Simul. article](https://journals.aut.ac.ir/article_5612_04089d3f0991a7abe10f1f5cca6691b0.pdf); [arXiv 2505.19311](https://web3.arxiv.org/pdf/2505.19311)

### Inferences
- Proposed split of checks (my synthesis):

| Check | Needs | Suggested implementation | Pass/fail output |
|---|---|---|---|
| Model builds; joint count/type/axis sign as intended | static | compile + counts; move each joint +δ and assert a named frame moves in the expected direction | boolean + diff vs spec |
| Mobility / over- or under-constraint | kinematics (rank) | Grübler count as hint; numerically, rank of constraint Jacobian at several poses (MuJoCo `nv` minus rank of equality Jacobian `efc_J`) | DOF == intended DOF |
| Range of motion / joint limits reach required travel | kinematics | per-joint sweep to first contact on B-rep (or mesh distance) | travel_mm ≥ required |
| Collision/self-collision through full travel | kinematics | grid/Latin-hypercube over joint space (a 3-axis gantry is only 3-D), exact boolean-volume or min-distance per pose; add conservative clearance; multi-joint, not one-at-a-time | max overlap volume == 0; min clearance ≥ threshold |
| Reachable workspace / build volume | kinematics | forward kinematics of tool frame over joint box; compare convex/axis-aligned extent to spec | volume ≥ spec |
| Closed-loop feasibility (CoreXY, four-bar, dual rails) | kinematics, but engine-assisted | drive loop in MuJoCo and monitor equality-constraint residual and solver iterations along the path | residual < tol everywhere; no divergence |
| Singularities / binding | kinematics (+ friction dynamics for binding) | condition number of loop Jacobian along path; in dynamics, spike in required actuator force | cond < limit |
| Actuator sizing (stepper torque/speed margins) | dynamics (inverse) | prescribe trapezoid/S-curve trajectory at target accel/jerk, `mj_inverse` → joint forces → reflect through pulley radius/screw lead; compare with motor torque-speed curve incl. rotor inertia as `armature` | margin ≥ factor at all t |
| Gravity sag / holding (Z axis back-drive, cantilever) | statics/dynamics | settle under gravity with actuators off / holding torque only | drift < tol |
| Static stability / tipping | statics | CoM projection vs support polygon over workspace and under peak accel reaction | margin > 0 |
| Belt tension/deflection, natural frequencies, input-shaping relevance | dynamics with compliance | lumped belt springs (tendon stiffness) or Chrono/Exudyn flexible elements; linearise (`mjd_transitionFD`) for modal frequencies | f1 ≥ target Hz |
| Cable / drag-chain routing | kinematics + geometry | swept envelope check; flex/cable sim only if needed | no clash, bend radius ≥ min |

- Physics-engine contact is a poor primary clash detector for CAD verification: it works on convex hulls/decompositions (false positives on concave parts, false negatives after simplification), tolerates small penetrations by design, and contact between nominally-sliding parts (carriage on rail) must be excluded anyway. Exact B-rep interference at sampled poses is more trustworthy; the engine's value is producing consistent poses for closed loops (which the CAD layer in text-to-cad explicitly cannot pose) and force/torque data.
- For a gantry the intended motion is prescribed, so **inverse dynamics on a prescribed trajectory** is cheaper and more robust than tuning a forward controller: no contact, no gain tuning, deterministic, and it directly yields the torque-vs-speed trace needed for stepper margin checks.
- Rigid-body engines will not predict ringing/resonance unless compliance is deliberately added (belt stiffness, frame flex); a pass from a rigid model says nothing about input-shaper frequency. That check belongs to FEA modal analysis or a lumped model, not to the default motion verifier.

### Gaps
- No authoritative published checklist for "motion verification of a machine design" (as opposed to robot model health) was found; the table above is synthesis.
- No sourced numbers for stepper sizing margins, belt pretension, or drag-chain bend-radius rules were collected (vendor application notes not searched successfully).
- No source found on swept-volume (continuous) clash detection in OCCT/build123d vs sampled-pose; continuous guarantees remain an open question.

## 4. Modelling a 3D-printer or CNC gantry specifically

### Takeaway
I found no published MuJoCo, Chrono or Gazebo model of a Voron/Prusa/CoreXY printer or CNC router; academic CoreXY models are hand-derived Lagrangian or spring-mass models, and community tooling simulates firmware/motion planning rather than rigid-body mechanics. A gantry model therefore has to be built from first principles — which is feasible because the modelling primitives (slide joints, joint-equality couplings for screws and belts, tendons, DC-motor actuators) exist.

### Cited Findings
- Search for CoreXY/Voron simulations in MuJoCo, Gazebo or Chrono returned none; closest items are CAD "digital twins" in SolidWorks, a consumer "3D Printer Simulator" (Ender-3 only, CoreXY/delta planned) and MK404, a hardware-accurate Prusa firmware emulator (not rigid-body dynamics). **[search summary]** — [3D Printing Industry on 3D Printer Simulator](https://3dprintingindustry.com/news/3d-printer-simulator-emulates-fdm-3d-printing-workflows-240635/); [MK404](https://vintagepc.github.io/MK404)
- Search for Voron 2.4/Trident multibody or Simscape models returned no implementation; only a planned Voron 2.4 benchmarking project spec and the academic CoreXY papers listed in §3. **[search summary]** — [PCBWay project page](https://www.pcbway.com/project/shareproject/Wentink_Motion_CoreXY_Kinematic_Dynamics_Spectral_Resonance_Benchmarking_10b8d635.html)
- `klipper_estimator` (Annex Engineering) re-implements Klipper's kinematics/motion planner offline: `estimate` mode gives detailed print statistics, and **`dump-moves` mode "dumps planning data for every move in a file"**; pre-built Linux binaries; delta kinematic limits are not implemented. — [klipper_estimator README](https://github.com/Annex-Engineering/klipper_estimator)
- Klipper resonance tooling is measurement-based, not simulation: `calibrate_shaper.py` and Klippain Shake&Tune analyse accelerometer data to choose shaper type, resonant frequency and damping ratio. **[search summary]** — [klippain-shaketune](https://github.com/frix-x/klippain-shaketune)
- Test-target CAD: Voron publishes CAD on GitHub (VoronDesign/Voron-0, Voron-Trident with 250/300/350 mm configurations, Voron-2; Stealthburner CAD in STEP); a forum user notes the Voron 2.4 STEP on GitHub covered only the 250 mm size; Voron's own CAD files are "essentially STEP files in F3D format" (no parametric history), which motivated a community parametric Fusion reconstruction (matthewlloyd/Voron-Parametric); LDO kit repos (MotorDynamicsLab/LDOVoronTrident, LDOVoron0) hold supplementary kit resources. **[search summary]** — [Voron-Trident repo](https://github.com/VoronDesign/Voron-Trident); [Voron-0 repo](https://www.github.com/VoronDesign/Voron-0); [Voron forum thread](https://forum.vorondesign.com/threads/step-files-for-300x300-voron-2-4.771/); [Voron-Parametric listing](https://awesome.ecosyste.ms/projects/github.com%2Fmatthewlloyd%2FVoron-Parametric)
- Other open CoreXY designs surfaced: V1 Engineering MP3DP v5, aetriq/ChimeraiXY, lerouxb/corexy, 247printing/247zero. **[search summary]** — [MP3DP docs](https://docs.v1e.com/mp3dp/); [ChimeraiXY](https://github.com/aetriq/ChimeraiXY); [lerouxb/corexy](https://github.com/lerouxb/corexy); [247zero](https://github.com/247printing/247zero)
- Engine primitives that map onto gantry elements: joint-equality polynomial coupling (linear term = ratio) between hinge and slide joints; tendon-length equality; `dcmotor` actuator; joint `armature`, `damping`, `frictionloss`; `actuatorfrcrange`. — [MuJoCo XMLreference.rst](https://github.com/google-deepmind/mujoco/blob/main/doc/XMLreference.rst); [MuJoCo changelog](https://github.com/google-deepmind/mujoco/blob/main/doc/changelog.rst)
- text-to-cad already encodes lead screws (`screw_pair`, pitch in mm/turn on a cylindrical joint) and rack-and-pinion as couplings exported to `<equality><joint>`; its kinematics reference lists "a hinge, a robot arm, a gearbox, a lead screw" as in-scope mechanisms. — [text-to-cad kinematics.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/cad/references/kinematics.md)
- Newton 1.8.0 has experimental routed tendons "with anchors, pinholes, circular rollers, finite capstan friction" — the closest thing to an explicit belt-around-pulleys model in the engines reviewed. — [Newton CHANGELOG](https://github.com/newton-physics/newton/blob/main/CHANGELOG.md)

### Inferences
- A workable MuJoCo abstraction for a CoreXY gantry (my proposal, not found in a source): bodies = frame (fixed), Y-gantry beam (slide y), toolhead carriage (slide x on the beam), bed (slide z), motors A/B (hinge); do **not** simulate belts as bodies. Encode CoreXY kinematics as a *fixed tendon* per belt with coefficients over (x, y, motor angle): belt A length = x + y − r·θA = const, belt B = x − y − r·θB = const, enforced by a tendon equality (or, for a compliant belt, tendon stiffness = EA/L giving a first resonance). Z leadscrews = joint equality between screw hinge and bed slide with `polycoef a1 = lead/2π`; triple-Z = three screw joints coupled or independent. Linear rails = slide joints with `frictionloss` (preload drag) and `range` (travel). Motors = `dcmotor`/position actuators with rotor inertia as `armature` and holding torque as `actuatorfrcrange`.
- Dual parallel rails/dual-Y gantries are over-constrained by Grübler count; in a tree-based engine model one rail as the joint and represent the second as (optionally) a soft `connect`/weld whose constraint force is a proxy for racking/binding load. Because MuJoCo cannot close a loop with a slide equality, the closure has to be expressed through connects on a hinge/ball surrogate or by coupling two slide joints with a joint equality.
- G-code replay pipeline: slicer G-code → `klipper_estimator dump-moves` (or a simple trapezoid planner) → per-axis position/velocity/acceleration time series → CoreXY inverse kinematics → `mj_inverse` for required motor torques + kinematic clash sweep along the tool path. This reuses the real firmware's acceleration/junction logic rather than reinventing it.
- Voron STEP assemblies have no joint metadata, so they are test targets for "articulate a vendor STEP" (group parts into links, infer axes from geometry) rather than drop-in mechanisms; text-to-cad documents exactly such a "from a vendor STEP" workflow for robot arms.

### Gaps
- No existing open rigid-body model of a Voron/Prusa/RatRig/PrintNC machine was found; absence is from two searches only, so GitHub-hosted hobby attempts may exist.
- RatRig, PrintNC and Prusa CAD availability/format (STEP vs Fusion vs OpenSCAD) was not confirmed — searches returned only Voron material.
- Klipper's own batch/"simulavr" test modes and kinematics libraries (e.g. Python ports of CoreXY/delta kinematics) were not verified this session.
- `klipper_estimator dump-moves` output format/units and whether it emits per-stepper or Cartesian moves were not checked.

## 5. Evidence on LLM agents writing MJCF/URDF and simulation setups (2024–2026)

### Takeaway
Published evidence is dominated by articulated-object reconstruction (cabinets, appliances), where even the best systems are far from reliable — headline success rates of 75% fall to ~40–50% under independent re-evaluation — and by robot-morphology generation inside constrained templates. For engineered mechanisms the only quantified LLM work found is linkage synthesis with symbolic over/under-constraint feedback. No benchmark was found that measures an LLM agent producing a simulation-ready machine (gantry/gearbox) model from CAD.

### Cited Findings
- Articulate-Anything (arXiv 2410.13882): VLMs generate code compiled into simulator-ready articulated assets with an actor–critic refinement loop; authors report raising PartNet-Mobility success "from 8.7–12.2% to 75%" versus prior work (URDFormer, Real2Code). **[search summary]** — [arXiv 2410.13882](https://arxiv.org/html/2410.13882v4)
- Independent comparison in LAM: Language Articulated Object Modelers (CVPR 2026): Articulate-Anything joint success 40.3% on a five-class benchmark and 48.9% on general classes; Real2Code 13.5% (five classes); URDFormer 14.6% (general classes). Different benchmark from the original, figures via a secondary summary. **[search summary]** — [LAM paper notes](https://en.papernotes.org/CVPR2026/3d_vision/lam_language_articulated_object_modelers/); [LAM CVPR 2026 paper](https://openaccess.thecvf.com/content/CVPR2026/papers/Gao_LAM_Language_Articulated_Object_Modelers_CVPR_2026_paper.pdf)
- Failure modes attributed to prior systems by URDF-Anything (arXiv 2511.00940, NeurIPS 2025): Real2Code's oriented-bounding-box part representation loses geometric detail and limits kinematic accuracy; Articulate-Anything depends on a mesh asset library and iterative VLM refinement (fragile, limited to library content); URDFormer assigns joint parameters by discrete classification and retrieves meshes (low fidelity). URDF-Anything reports a "physical executability rate … substantially higher than baselines (50% improvement)". **[search summary]** — [arXiv 2511.00940](https://arxiv.org/html/2511.00940v1)
- Follow-ups: URDF-Anything+ (arXiv 2603.14010, NeurIPS 2026 poster) claims gains in geometry, joint-parameter estimation and physical executability; ArtiWorld/Arti4URDF (arXiv 2511.12977) reports SOTA joint-type prediction and joint-axis localisation. **[search summary]** — [NeurIPS 2026 poster](https://neurips.cc/virtual/2026/poster/150077); [arXiv 2511.12977](https://arxiv.org/html/2511.12977v1)
- Robot-design generation: RobotDesignGPT (arXiv 2601.11801) uses VLMs to emit URDF/MJCF with a visual feedback loop comparing renders to references; RoboMorph (arXiv 2407.08626) has an LLM propose designs within a robot grammar, compiled to XML and evaluated in MuJoCo/MJX; Debate2Create (arXiv 2510.25850) restricts the design agent to bounded parameters in MJCF templates with fixed topology. **[search summary]** — [arXiv 2601.11801](https://arxiv.org/html/2601.11801); [arXiv 2407.08626](https://arxiv.org/pdf/2407.08626v3); [arXiv 2510.25850](https://arxiv.org/pdf/2510.25850)
- An RSS 2026 paper (proceedings XXII, p194; the search summary labelled it "AID-SR" and mis-dated it 2022) has a Coder agent write MuJoCo XML checked by layered feedback including a deterministic physical-stability check; example errors include an unrecognised XML attribute and tendon sites placed in the wrong position. **[search summary; title/date uncertain]** — [RSS proceedings p194](https://roboticsproceedings.org/rss22/p194.pdf)
- SR-Platform (arXiv 2605.14700): natural-language → MJCF scene pipeline with industrial layout checks including clearance verification before assembly. **[search summary]** — [arXiv 2605.14700](https://arxiv.org/pdf/2605.14700)
- Mechanism synthesis: Gandarela et al., "Controlled Agentic Planning & Reasoning for Mechanism Synthesis" (arXiv 2505.17607, 2025) — dual-agent design/critique loop for planar mechanisms, introduces the MSynth benchmark; arXiv 2604.27962 (Apr 2026) — proposer/critic/planner/refiner agents with symbolic simulation diagnostics; 78.6% of refinement trajectories improve; diagnosed failure modes overconstraint 56.3% / underconstraint 35.6%; symbolic lifting reduced variance across LLMs. **[search summary]** — [arXiv 2505.17607](https://arxiv.org/html/2505.17607v1); [emergentmind 2604.27962](https://www.emergentmind.com/papers/2604.27962)
- Practitioner-encoded failure list (from a tool built for LLM agents): frame placement, joint-axis semantics/sign, units, mesh scale, inertial data; "a file can pass every check while placing a joint in the wrong spot"; lint codes for interpenetration at rest, mm-read-as-metres, joints outside limits at rest, double-counted mass, colliding visuals, zero-count joints/actuators. — [text-to-cad robot-simulation SKILL.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/SKILL.md); [text-to-cad mjcf-checks.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/references/mjcf-checks.md)
- Signal that LLM-driven development of multibody code is already mainstream in one engine: Exudyn states it has been "heavily developed with Anthropic's Claude Code" since v1.11.0. — [Exudyn README](https://github.com/jgerstmayr/EXUDYN)

### Inferences
- The research literature's task (infer articulation from images/meshes) is harder and different from the team's task (the agent *authors* the joints in code-CAD, so axes/limits are known by construction). The relevant lesson is structural: systems that generate *code/structured programs* with a simulator- or critic-in-the-loop outperform direct prediction, and systems that restrict the LLM to a constrained interface (grammar, bounded template parameters, generated-never-edited files) avoid whole classes of invalid output.
- The failure taxonomy that keeps recurring — wrong axis/sign, wrong frame origin, mm/m scale, missing/garbage inertias, interpenetrating initial state, unstable contact from bad collision geometry — is mostly detectable with cheap deterministic checks (compile, counts, at-rest contacts, scale heuristics, per-joint nudge direction test) before any expensive simulation; only "joint in the wrong place but everything compiles" needs either a rendered frame for a VLM/human or an assertion against design intent (e.g. tool-frame displacement per unit joint motion).
- Deriving the sim model mechanically from CAD (rather than letting the LLM write MJCF) removes inertia, scale and frame errors; the LLM-authored residue is small and reviewable: collision choices, friction/armature/damping, actuators, and the test trajectory with its pass thresholds.

### Gaps
- arxiv.org and huggingface.co were unreachable, so every paper figure above is from search summaries/secondary sites, not the papers; the 75% (Articulate-Anything), 40.3/48.9/13.5/14.6% (LAM table), 78.6/56.3/35.6% (2604.27962) numbers should be re-checked against the PDFs.
- No quantitative study found of LLM success/failure writing MJCF or URDF for *machines* (gantries, gearboxes), nor per-category error rates (axis vs inertia vs scale vs penetration).
- AssemCAD, RoboCasa/Genesis-style generative pipelines, and any Zoo simulation features were not located.
- The RSS p194 paper's real title and exact claims are unverified.

## 6. Presenting motion to the human

### Takeaway
Headless options are now good: MuJoCo 4.0 ships an official browser viewer (MuJoCo Studio web, WASM client in a pip wheel) and a headless render sample with video output; `mjviser`/viser and Newton's viewer backends (viser, rerun, USD) give web/recordable views; and the CAD side can play joint "configuration sequences" directly in a CAD viewer without any physics.

### Cited Findings
- MuJoCo Studio Web Viewer: `mujoco-studio --gfx=web` / `mujoco.studio.launch_web`; the browser client ships as the platform-independent `mujoco-studio-wasm` wheel (auto-installed by `mujoco-studio`); documented under "MuJoCo Studio … web viewers" (4.0.0/4.0.1). — [MuJoCo changelog](https://github.com/google-deepmind/mujoco/blob/main/doc/changelog.rst); [MuJoCo python.rst](https://github.com/google-deepmind/mujoco/blob/main/doc/python.rst)
- Offscreen rendering from Python: `mujoco.Renderer` with GL contexts (classic OpenGL; user must set up a working GL context) and a Filament `Renderer` class under `mujoco.rendering.filament`; `sample/render.cc` renders headless to PNG and (4.0.0) multi-frame raw RGB24 video; Filament depth/segmentation renders supported. — [MuJoCo python.rst](https://github.com/google-deepmind/mujoco/blob/main/doc/python.rst); [MuJoCo changelog](https://github.com/google-deepmind/mujoco/blob/main/doc/changelog.rst)
- Official MuJoCo WebAssembly/JavaScript bindings exist; zalo/mujoco_wasm (MIT) is now "just a small demo suite" on top of "the official MuJoCo WebAssembly Bindings", loading MuJoCo 3.12.0 models in the browser with three.js. — [mujoco_wasm README](https://github.com/zalo/mujoco_wasm)
- `mjviser`: "A web-based MuJoCo viewer built on Viser"; `uvx mjviser path/to/model.xml` or `pip install mjviser`; default port 8080; notes MuJoCo could not yet build on Python 3.14+ at time of writing. — [mjviser README](https://github.com/mujocolab/mjviser)
- Newton viewer backends: `gl, usd, rtx, rerun, viser, or null`; `ViewerViser` got a `host` bind-address argument in 1.8.0; `ViewerUSD` exports primitives as native UsdGeom Gprims. — [Newton README](https://github.com/newton-physics/newton); [Newton CHANGELOG](https://github.com/newton-physics/newton/blob/main/CHANGELOG.md)
- MuJoCo can export to USD for external renderers such as Omniverse or Blender ("higher quality rendering capabilities not provided by the default renderer"). — [MuJoCo python.rst](https://github.com/google-deepmind/mujoco/blob/main/doc/python.rst)
- CAD-side animation without physics: text-to-cad `configuration_sequence(assembly, name, waypoints_or_fn, sweep={joint: (from, to)}, duration=…)` sequences are played in its CAD viewer (play, pause, scrub, loop, speed); snapshots at named poses via `cad model snapshot "$ID" out.png --pose home` and `cad urdf snapshot robot.urdf out.png --pose '{"elbow": 45}'`; text-to-cad also exports GLB and produces Blender "stills, turntables, and films". — [text-to-cad kinematics.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/cad/references/kinematics.md); [text-to-cad mjcf-checks.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/references/mjcf-checks.md); [text-to-cad README](https://github.com/earthtojake/text-to-cad)
- text-to-cad deliberately does not render MJCF itself ("No `cad` command draws an MJCF"); for kinematics pictures it snapshots the CAD model or URDF, and for dynamics the person opens MuJoCo Studio. — [text-to-cad mjcf-checks.md](https://github.com/earthtojake/text-to-cad/blob/main/skills/robot-simulation/references/mjcf-checks.md)

### Inferences
- Two complementary artefacts suit the human-in-the-loop: (1) a deterministic MP4/GIF or contact-sheet of key frames (start, mid, end of travel, worst-clearance pose) rendered headlessly and attached to the verifier report, with overlays of the measured numbers; (2) an interactive web view (MuJoCo Studio web or viser) for scrubbing. The frames in (1) can also be fed back to the model as images for a "does positive X move the toolhead to the right?" sanity check.
- Because the sim trajectory is just `qpos(t)`, an animated glTF/GLB of the *exact CAD meshes* (node transforms keyframed from body poses) is a renderer-independent deliverable viewable in any three.js viewer; this is straightforward to produce (e.g. via trimesh/pygltflib) but I found no off-the-shelf MuJoCo→animated-glTF exporter this session.
- In a GPU-less sandbox, classic-GL offscreen rendering via OSMesa (software) or EGL (if a device is exposed) is the conservative choice; the newer Filament path should be tested in the target container before being relied on.

### Gaps
- rerun, meshcat and three.js `urdf-loaders` were not examined from primary sources this session (fetch of urdf-loaders README succeeded but was not analysed); their current versions/capabilities are unverified.
- No source confirmed an existing animated-glTF export path from MuJoCo or build123d joint sequences.
- Software-rendering performance/compatibility of MuJoCo 4.0's Filament renderer in headless containers is unknown.
