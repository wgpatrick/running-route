## 1. Parametric open libraries (build123d / CadQuery / FreeCAD / OpenSCAD)

### Takeaway
For a build123d agent, `bd_warehouse` (Apache-2.0) is the only library that is native, permissively licensed, standards-keyed, and already carries interface helpers (clearance/tap/insert/press-fit holes, named `RigidJoint`s) plus some real engineering data (its bearing CSV includes dynamic/static load ratings, speed limits, mass and designation). Everything else is either CadQuery-era (cq_warehouse, cq_gears), geometry-only (gear generators, cq-electronics), copyleft and in another kernel/language (NopSCADlib GPL-3, FreeCAD Fasteners), or a loose file dump (FreeCAD-library, ~5 GB, CC-BY 3.0) — useful as data sources to port, not as dependencies.

### Cited Findings

**bd_warehouse (gumyr)**
- Licence Apache-2.0; `pip install bd_warehouse`; requires Python >=3.10,<3.15, `build123d >=0.12.0,<0.14.0` and `bd_materials >=0.2.0,<0.3.0`; version is derived from git tags (setuptools_scm), size tables ship as packaged `*.csv` [1st-hand] — [pyproject.toml](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/pyproject.toml)
- Repo page showed 114 stars, 33 forks, 277 commits on `main`, no GitHub Releases entries [1st-hand] — [github.com/gumyr/bd_warehouse](https://github.com/gumyr/bd_warehouse)
- Documented sub-packages (docs toctree): bearing, bushing, fastener, flange, gear, openbuilds, o_rings, pipe, retaining_ring, shaft_key, sprocket, thread; `chain` and `finger_jointed_boxes` are commented out of the docs index [1st-hand] — [docs/index.rst](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/docs/index.rst)
- Fasteners are selected by class + standard string + size string, e.g. `HexNut(size="M3-0.5", fastener_type="iso4032")`, `SetScrew(size="M6-1", fastener_type="iso4026", length=10*MM)`. Standards covered include nuts (din1587, iso4032/4033/4035/4036, din1665, din557), screws (iso7380_1/_2, iso14580, iso7048, iso1207, iso2009, iso14581/14582, iso10642, iso7046, iso4017, din931, iso4014, din1662/1665, asme_b_18.6.3, iso1580, iso14583, din967, iso7045, iso2010, iso7047, iso14584, iso4026, iso4762, asme_b18.3) and washers (iso7089/7090/7091/7092/7093/7094, din6797, asme_b18.21.1). Both metric and imperial sizes are supported [1st-hand] — [docs/fastener.rst](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/docs/fastener.rst)
- Fastener classes expose discovery class-methods an agent can call instead of guessing: `types()`, `sizes(type)`, `select_by_size()`, `nominal_length_range[type]`, plus `info`, `hole_locations`, `nut_thickness`, and `Screw.min_hole_depth`; hole data tables exist for clearance holes and tap holes (`clearance_hole_data`, `tap_hole_data`, drill sizes). The docs note standards give min/max dimension ranges and the library picks the maximum-material size so clearances are not violated by a real part [1st-hand] — [docs/fastener.rst](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/docs/fastener.rst)
- Vendor-keyed non-standard hardware exists too: the docs' example BOM output is `{'BradTeeNut(Hilitchi): M8-1.25': 1, 'HeatSetNut(McMaster-Carr): M4-0.7': 3, 'CounterSunkScrew(iso10642): M4-0.7x20': 3}` — i.e. the library can already emit a fastener count dictionary keyed by type(standard): size; `HeatSetNut` must be placed with an `InsertHole` [1st-hand] — [docs/fastener.rst](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/docs/fastener.rst)
- Bearings: `SingleRowDeepGrooveBallBearing`, `SingleRowCappedDeepGrooveBallBearing`, `SingleRowAngularContactBallBearing`, `SingleRowCylindricalRollerBearing`, (`SingleRowTaperedRollerBearing` partly hidden in docs), all of type "SKT"; sizes are strings like `"M8-22-7"`. Docs: bearings "are created as build123d Compound/Assemblies and with accurate external dimensions but simplified internal structure to avoid excess creation time" [1st-hand] — [docs/bearing.rst](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/docs/bearing.rst)
- The deep-groove bearing CSV header is `Size, d, D, B, C, C0, Pu, Speed-reference, Speed-limit, mass, Designation, d1, D1, D2, r12, da, Da, ra, kr, f0` (first row: `M3-10-4, 3, 10, 4, 0.54, 0.18, 0.007, 130000, 80000, 0.0015, 623, …`). So basic dynamic rating C, static rating C0, fatigue limit Pu, speed limits, mass, designation, abutment dimensions (da/Da/ra) and the ISO 281/76 factors kr/f0 are in the packaged data even though the geometry class does not surface them as an API [1st-hand] — [single_row_deep_groove_ball_bearing_parameters.csv](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/src/bd_warehouse/data/single_row_deep_groove_ball_bearing_parameters.csv)
- Bearing objects carry `RigidJoint("a")` / `RigidJoint("b")` at the two end faces "to match PressFitHole expectations", and define a default press-fit seat as "the bearing outline less the interference" [1st-hand] — [bearing.py](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/src/bd_warehouse/bearing.py)
- OpenBuilds module: profiles `VSlotLinearRailProfile`, `CBeamLinearRailProfile`; parts `VSlotLinearRail`, `CBeamLinearRail`, `CBeamEndMount`, gantry plates, `EccentricSpacer`, `FlexibleCoupler`, `LockCollar`, `MetricLeadScrew`, `AcmeAntiBacklashNutBlock8mm`, `XtremeSolidVWheel`, `TNut`, `LBracket`, `ShimWasher`, `SpacerBlock`, `RouterSpindleMount`, and `StepperMotor(motor_type: "Nema17" | "Nema23" | "Nema23HighTorque")`; plus pre-built assemblies (e.g. `CBeamEndAssembly` = end mount + NEMA 23 + coupler + bearing). Parts define named joints (`RigidJoint`, `RevoluteJoint`, `LinearJoint`) that are connected with `a.joints["x"].connect_to(b.joints["y"])`. The docs warn: "All Joints are currently experimental and subject to change" [1st-hand] — [open_builds.py](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/src/bd_warehouse/open_builds.py); [docs/openbuilds.rst](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/docs/openbuilds.rst)
- Gears: `SpurGear`, `HelicalGear`, `RackGear`, `Worm`/`WormWheel`/`WormGear`, `BevelGear`, `MiterGear` (involute and spherical-involute profiles). Threads: `IsoThread`, `AcmeThread`, `MetricTrapezoidalThread`, `TrapezoidalThread`, `WhitworthThread`, `BSPPThread`, `PlasticBottleThread`. Flanges: Blind/Lapped/SlipOn/SocketWeld/WeldNeck with `FlangeClass`/`FaceType`; pipes keyed by `Nps`; `Sprocket` [1st-hand] — [docs/gear.rst](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/docs/gear.rst); [docs/thread.rst](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/docs/thread.rst); [docs/flange.rst](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/docs/flange.rst)

**bd_materials (mass assignment companion)**
- Gives a part a named material and returns mass and mechanical/thermal property *ranges*: `metals.aluminum(metals.Alu.G7075_T6, finishes.anodize(...))`, `part.material.mass(volume_mm3=8000)` (grams). It states it "is **not a materials database**", values are "typical values only" (min–max `Range`, single representative density) and "In detailed design, use the actual product's data sheet". 39 metal grades, 26 plastic grades, plus resins, glass, wood, etc. [1st-hand] — [bd_materials README](https://raw.githubusercontent.com/gumyr/bd_materials/main/README.md)

**cq_warehouse (gumyr, CadQuery predecessor)**
- README still describes it as the CadQuery parametric parts collection, installed from GitHub (`pip install git+https://github.com/gumyr/cq_warehouse.git`), with a `dev` branch; no mention of deprecation in the README itself [1st-hand] — [cq_warehouse README](https://raw.githubusercontent.com/gumyr/cq_warehouse/main/README.md)

**Gear generators**
- `py_gearworks` (the `GarryBGoode/gggears` URL serves the identical README, i.e. gggears was renamed): build123d-based, `pip install py-gearworks`; spur, helical, bevel, cycloid, inside-ring; profile shift, undercut, crowning, root/tip fillets; backlash-controlled positioning is partly work-in-progress; racks partial. Explicitly: "Design calculations related to strength, pitting, efficiency may be implemented in the future - but currently not supported" [1st-hand] — [py_gearworks README](https://raw.githubusercontent.com/GarryBGoode/py_gearworks/main/README.md)
- `cq_gears` v0.51: CadQuery; spur, helical, herringbone, ring, planetary sets, bevel, rack; README self-describes as "Work in progress... Might be unstable, but somewhat usable" and requires a development CadQuery build [1st-hand] — [cq_gears README](https://raw.githubusercontent.com/meadiode/cq_gears/main/README.md)

**cq-electronics / cq-kit**
- `cq-electronics`: "Pure CadQuery models of various electronic boards and components... intended to be representations rather than detailed models. That is, the major dimensions are accurate and there are enough features to make the component recognisable"; on PyPI [1st-hand] — [cq-electronics README](https://raw.githubusercontent.com/sethfischer/cq-electronics/main/README.rst)
- `cq-kit` (MIT, PyPI `cqkit`): not a parts library — it is CadQuery utilities: file I/O (STEP, IGES, STL, LDraw), extra `Selector` classes, construction helpers, shape analysis/debug printing [1st-hand] — [cq-kit README](https://raw.githubusercontent.com/michaelgale/cq-kit/master/README.md)
- `cadquery-contrib` now ships an MCP server "for AI assistants (Claude, etc.) to execute CadQuery scripts and render 3D models" alongside example scripts [1st-hand] — [cadquery-contrib README](https://raw.githubusercontent.com/CadQuery/cadquery-contrib/master/README.md)

**FreeCAD Fasteners workbench (shaise)**
- Wrapper around the `screw_maker` macro; scriptable: `screwobj = sm.createFastener('ISO7046', 'M6', '8', 'simple')`; thread rendering is optional and slow ("generating threads takes considerable amount of time"). Very broad standards coverage and actively maintained through 2026: release notes list V0.5.51 (12 Apr 2026, add DIN7979), V0.5.53 (07 Jun 2026, DIN trapezoidal rod), V0.5.65 (29 Aug 2026, insert fasteners in active assembly), and **V0.6.00 (12 Nov 2026): "Update license to LGPL"**; 2024 notes add many ISO pins (ISO 2338–8752), ISO nuts (ISO 4161, 7040, 10511 …), ASME B18.6.1 wood screws, nails, thumb screws [1st-hand] — [FastenersWB README](https://raw.githubusercontent.com/shaise/FreeCAD_FastenersWB/master/README.md)

**FreeCAD-library (parts library)**
- "maintained by the community of users of FreeCAD and is not part of the FreeCAD project"; parts should be in `.FcStd` and `.stp` (optionally `.stl`); "All Parts in this repository are licensed under CC-BY 3.0... Each Part is copyrighted by and should be attributed to its respective author(s). See commit details to find the authors"; "the library is huge in size (+/- 5 Gb)" [1st-hand] — [FreeCAD-library README](https://raw.githubusercontent.com/FreeCAD/FreeCAD-library/master/README.md)

**NopSCADlib (nophead, OpenSCAD)**
- GPL-3.0; "An ever expanding library of parts modelled in OpenSCAD useful for 3D printers and enclosures for electronics"; includes Python scripts that "generate Bills of Materials (BOMs), STL files for all the printed parts, DXF files for CNC routed parts in a project and a manual containing assembly instructions and exploded views by scraping markdown embedded in OpenSCAD comments". Repo page: 1.7k stars, 1,661 commits [1st-hand] — [NopSCADlib readme](https://raw.githubusercontent.com/nophead/NopSCADlib/master/readme.md); [repo page](https://github.com/nophead/NopSCADlib)
- Vitamin categories relevant to a gantry (from the README table of contents): Ball_bearings, Bearing_blocks, Belts, BLDC_motors, Blowers, Box_sections, Circlips, Extrusion_brackets, Extrusions, Fans, Gear_motors, Geared_steppers, Hot_ends, Inserts, Leadnuts, Linear_bearings, Magnets, Microswitches, Nuts, O_ring, PCBs, Pillow_blocks, PSUs, Pulleys, Rails, Rod, Rod_ends, SBR_rails, Screws, Servo_motors, Shaft_couplings, Sheets, SK_brackets, Springs, Stepper_motors, Tubings, Washers, Wire, Zipties; utilities include Core_xy, Gears, Thread, Drag_chain. Each vitamin section documents typed "Properties" accessor functions (the object is an OpenSCAD list; fields are read by named functions) [1st-hand] — [NopSCADlib readme](https://raw.githubusercontent.com/nophead/NopSCADlib/master/readme.md)

**MCAD (OpenSCAD)**
- "components commonly used in designing and mocking up mechanical designs"; "All the files are licensed under the LGPL 2.1" unless a file's comments say otherwise; includes `motors`, `servos` and similar modules [1st-hand] — [MCAD README](https://raw.githubusercontent.com/openscad/MCAD/master/README.markdown)

### Inferences
- The practical "tier-0" catalog for a build123d agent is: bd_warehouse fasteners/bearings/threads/OpenBuilds + bd_materials for density + py_gearworks for gears. It is small (roughly: ISO/DIN/ASME fasteners, 5 bearing families, V-slot/C-beam, three NEMA motors) but it is legally clean (Apache-2.0), generated in-process (no network, no licence prompts), and discoverable by reflection (`types()`, `sizes()`), which directly counters hallucinated sizes: the agent can only instantiate sizes that exist in the CSV.
- The bd_warehouse bearing CSV is an under-used asset: C, C0, Pu, speed limit and mass are already there, so an ISO 281 L10 check and a mass rollup can be driven from the same row that generates geometry. The catalog designation column ("623", "618/4") gives a supplier-neutral part number.
- Geometry in these libraries is deliberately simplified (bearings: "accurate external dimensions but simplified internal structure"; cq-electronics: "representations"). That is the *right* fidelity for interference and motion checks, and means little defeaturing is needed for library parts — unlike vendor STEP.
- GPL-3 NopSCADlib and the (until Nov 2026 non-LGPL) FreeCAD Fasteners code cannot be vendored into a proprietary agent product, but their dimension tables are a guide to *which* part families a 3D-printer-class machine needs; NopSCADlib's vitamin list is the closest thing to a ready-made ontology for printer-gantry COTS parts. Whether dimension tables themselves can be copied is a legal question I did not research.
- Notable holes in open parametric coverage for a gantry: MGN-style profile linear rails/carriages, ball screws and nut housings, GT2 belts/pulleys/idlers, shaft couplers beyond the OpenBuilds one, NEMA motors with real variants (length, shaft, torque), 2020/3030 T-slot (non-V-slot) extrusion and brackets, springs. These must come from vendor STEP or be written in-house as parametric classes.

### Gaps

- KiCad packages3D (STEP/WRL models): licence and coverage not checked this session; cq-electronics points to the "KiCad Packages3D Generator" on GitLab as a related project only.
- Voron/RatRig/OpenBuilds vendor CAD as *part* sources: see section 6 for the machine-level picture; per-part reuse terms not researched.
- Last-commit dates and release numbers for bd_warehouse, cq_warehouse, cq_gears, py_gearworks, cq-electronics, NopSCADlib: not obtainable (GitHub API/commit feeds blocked). cq_warehouse is, as far as I know, superseded by bd_warehouse, but its README does not say so.

## 2. Package managers / registries for parts, and how agent harnesses handle catalogs

### Takeaway
PartCAD is the only live "package manager for hardware" effort and in 2026 it has pivoted hard toward AI agents (Claude Code plugin, MCP server, `/pc:search`, `/pc:add-interfaces`) and toward a requirements→BOM→sourcing "digital thread"; but its supplier/purchase features are partly marked "in progress" and I could not verify the size or quality of its public index. The other prominent harness, text-to-cad (26k stars), has **no parts catalog at all** — it treats COTS parts as "vendor STEP" files that the user/agent supplies, converts once to a cached binary, and then handles vendor-geometry quirks in its motion/collision checker.

### Cited Findings

**PartCAD**
- Self-description (README, `devel` branch): "the programming language for manufacturable things. A package is a Git repository with a `partcad.yaml` that declares parts (CAD scripts or files), assemblies, materials and requirements. PartCAD renders, tests, simulates, analyses and documents them, and produces the bill of materials, the sourcing and the assembly instructions from that same source." Apache-2.0. Repo page: 530 stars, 47 forks, 1,600 commits on `devel` [1st-hand] — [PartCAD README](https://raw.githubusercontent.com/partcad/partcad/devel/README.md); [repo page](https://github.com/partcad/partcad)
- Part sources: CadQuery, build123d, OpenSCAD, Chili3D, SDF scripts; files in STEP, BREP, IGES, STL, 3MF, OBJ, glTF, FreeCAD, Fusion, SolidWorks, Inventor, CATIA V5, ACIS, Creo View, OpenUSD; KiCad PCBs; plugin packages (SolidCraft, Rhino). Assemblies: "Assembly YAML, URDF, or a STEP, Autodesk Fusion or Creo View file, with interfaces and mating as objects". Outputs include URDF, Gazebo and MuJoCo worlds, dimensioned drawings, PDF/HTML instruction books [1st-hand] — [PartCAD README](https://raw.githubusercontent.com/partcad/partcad/devel/README.md)
- Verification-relevant commands: `pc qual test` — "qualify: basic, topology (overlaps, untoleranced faces), simulation, plugins"; `pc cae` (FEA, modal, thermal, CFD); `pc qual test --simulation` (MuJoCo or Gazebo); `pc cam` (2.5D toolpaths); `pc instructions` (assembly book with BOM) [1st-hand] — [PartCAD README](https://raw.githubusercontent.com/partcad/partcad/devel/README.md)
- AI features: Agent Skills for Claude Code and Cursor installed by `pc init`; Claude Code plugin (`/plugin marketplace add partcad/partcad@plugin-dist`); slash commands `/pc:gen`, `/pc:gen-part`, `/pc:gen-assembly`, `/pc:gen-sketch`, `/pc:gen-scene`, `/pc:describe`, **`/pc:search` ("search the catalog")**, **`/pc:add-interfaces`**, `/pc:validate` (checks an object against its `requirements:` — "ports, interfaces and physics it measures"); an MCP server `pc mcp` ("list, inspect, render (as an image), test and export objects… behind one `execute` tool", listed in the MCP Registry); `--no-ansi` plain-text output for agents [1st-hand] — [docs/source/supported.rst](https://raw.githubusercontent.com/partcad/partcad/devel/docs/source/supported.rst)
- Interfaces: "Object-Oriented Programming approach to maintaining part interfaces and mating information" [1st-hand] — [supported.rst](https://raw.githubusercontent.com/partcad/partcad/devel/docs/source/supported.rst)
- Supply chain claims: README — "a Build vs Buy decision per line item, stock-based procurement for made parts, and automated purchasing from the command line"; supported-features list — "Parametric (hardware and software) bill of materials", "Publish models online on PartCAD.org", "Automated purchase of parts via the command line", but "Purchase of assemblies and parts online, both marketplace and SaaS *(in progress)*" and "Publish configurable parts and assemblies online *(in progress)*"; the IDE shows "supplier quotes" on a tab. No specific supplier names appear in the README or supported.rst [1st-hand] — [PartCAD README](https://raw.githubusercontent.com/partcad/partcad/devel/README.md); [supported.rst](https://raw.githubusercontent.com/partcad/partcad/devel/docs/source/supported.rst)
- Public index: the `partcad-index` repo root `partcad.yaml` reads `partcad: ">=0.8.0"`, `name: //pub`, with the comment "Before adding your own packages, browse sub-folders to find the most appropriate parent package" — i.e. a hierarchical public namespace `//pub/...` of community packages [1st-hand] — [partcad-index/partcad.yaml](https://raw.githubusercontent.com/partcad/partcad-index/main/partcad.yaml)
- Caching: "in memory, on disk, in memcached and in S3, so a team or a CI fleet renders each model once" [1st-hand] — [PartCAD README](https://raw.githubusercontent.com/partcad/partcad/devel/README.md)

**text-to-cad (earthtojake)**
- MIT; repo page shows 26.2k stars, 2.5k forks, 1,510 commits; a plugin of skills + MCP server for agent apps; models are Python scripts using build123d/OpenCASCADE; skills for CAD, PCB (KiCad), manufacturability checks, FEA (CalculiX), drawings, Blender renders, SendCutSend checks, URDF/SRDF/MJCF export [1st-hand] — [text-to-cad README](https://raw.githubusercontent.com/earthtojake/text-to-cad/main/README.md); [repo page](https://github.com/earthtojake/text-to-cad)
- No catalog: the CAD skill's only route for purchased parts is "Use a vendor STEP, an xbf or a scan in a model — `step.read`, `xbf.read` or `stl.read` in the body". Caching guidance: "A vendor STEP is converted to an xbf once (`cad step export vendor/motor.step vendor/motor.xbf`) and read with `xbf.read`, many times faster than parsing the STEP"; `step.read` is preferred where names, colours and materials from the file are wanted [1st-hand] — [skills/cad/SKILL.md](https://raw.githubusercontent.com/earthtojake/text-to-cad/main/skills/cad/SKILL.md); [references/model-contract.md](https://raw.githubusercontent.com/earthtojake/text-to-cad/main/skills/cad/references/model-contract.md)
- Its joint-range/collision checker has explicit rules for vendor-geometry artefacts (highly relevant to a verifier): (a) "A vendor often draws a motor or a servo as one solid, its case and its output (flange, horn) together" — a link bolted to that output is recognised as "turns on" the solid rather than colliding; if the output carries an arm/cam, "split the solid in the model"; (b) "A vendor's simplified parts are often drawn sunk into each other (a link a little too wide for its clevis, a carriage drawn inside its rail)" — such pairs are reported as "overlapping as drawn … by 180 mm^3, 1.0 mm deep" and only count as a stop when pushed ~0.6 mm deeper than drawn; (c) where a stop is produced by a vendor cover that the real hardware clears, "write the range you read from the hardware (the datasheet's travel…)" [1st-hand] — [skills/cad/SKILL.md](https://raw.githubusercontent.com/earthtojake/text-to-cad/main/skills/cad/SKILL.md)

**Zoo / KCL**
- The `KittyCAD/kcl-samples` repository is archived: "This repo is archived. To view KCL sample projects, go to https://zoo.dev/aquarium" [1st-hand] — [kcl-samples README](https://raw.githubusercontent.com/KittyCAD/kcl-samples/main/README.md)

### Inferences
- Two different design philosophies exist in the wild: PartCAD = *declared* catalog (packages, interfaces, requirements, BOM as first-class YAML objects, searchable by an agent); text-to-cad = *no catalog*, vendor STEP as opaque input plus a verifier that tolerates vendor modelling sloppiness. A gantry-designing agent needs both: a typed catalog for selection, and text-to-cad-style tolerance rules for whatever geometry the catalog returns.
- text-to-cad's "overlapping as drawn" and "turns on an output" rules are empirical evidence that raw vendor STEP breaks naive interference checks (carriages modelled inside rails, motor shaft fused to body). A COTS component record should therefore carry (i) an allow-list of expected contacts/overlaps with mating parts and (ii) a split into kinematic sub-bodies (rotor/stator, carriage/rail, nut/screw).
- PartCAD could be adopted as the *container format* for an in-house catalog (git repo + `partcad.yaml` + build123d scripts + STEP files + interfaces) without depending on its public index or its unfinished purchasing features; its Apache-2.0 licence and MCP server make that low-risk. Whether to depend on it is a product-maturity judgement I could not ground in release data.

### Gaps
- PartCAD: latest PyPI version/date; contents and count of the `//pub` index (which vendors' parts, licence of each); which LLM providers its older `ai:` part-generation used; which supplier/store providers actually work (README names none). Docs site (readthedocs) was not fetchable; only README, supported.rst and the index root file were read.
- "npm for mechanical parts" efforts other than PartCAD: none found in searches this session; not an exhaustive negative.
- Onshape standard content / FeatureScript libraries: not researched this session (no sources retrieved).
- Zoo/KCL current standard-parts library (beyond the archived samples repo): not verified.
- text-to-cad: whether community skills add catalogs (issues/PRs not read).

## 3. Vendor CAD sources, APIs and terms — what an automated agent may use

### Takeaway
No major mechanical catalog offers an open, self-serve, redistribution-friendly CAD API. McMaster has an official Product Information API but it is approval-gated (per-customer client certificate), and its site terms tie CAD use to purchasing from McMaster; MISUMI's CAD terms expressly forbid bulk acquisition and third-party provision; CADENAS's portal terms forbid AI use outside the service description and carry contractual penalties. The legally workable pattern for a small team is: (1) generate standard parts parametrically, (2) keep a small curated, human-downloaded, per-part-licence-recorded STEP cache for branded parts (not redistributed), (3) use the electronics distributors' official APIs (Nexar/Octopart, Digi-Key, Mouser) for price/stock, and (4) pursue a commercial agreement (TraceParts API, McMaster API approval) if catalog breadth is needed.

### Cited Findings

**McMaster-Carr**
- Official "Product Information API" exists: described as "an external method for programmatically retrieving our publicly available product information". Access is gated: McMaster "provides a client certificate and an accompanying password for each approved customer", the certificate must accompany every request, and a Log In request (certificate + username + password) returns an authorization token with an expiry. ### Inferences

  - MISUMI: **human download for own machine design only**; bulk/automated acquisition and third-party provision prohibited.
  - CADENAS/3Dfindit: **high risk** for automated/AI use without a contract (explicit AI clause and penalty schedule).

Safer architecture: the catalog record stores vendor SKU + URL + envelope/interface data authored in-house, and a *proxy geometry* (in-house simplified parametric model); the customer fetches the official STEP themselves if they want vendor-exact geometry.
- Facts and dimensions from datasheets (bore, OD, hole pattern, load rating, mass) are a different thing from the vendor's CAD file; building in-house parametric proxies from published dimensions avoids the CAD-file licences altogether. (General principle; I did not research jurisdiction-specific database rights.)

## 4. Working with imported STEP parts; representing a COTS part as a typed component; schemas/standards

### Takeaway
There is no adopted open schema that bundles geometry + interfaces + ratings + SKU for mechanical COTS parts in a form a code-CAD agent can consume; the closest industrial standard is the Asset Administration Shell "Technical Data" submodel (IDTA 02003, v2.0 March 2025) with ECLASS/IEC CDD property semantics, and the closest working practice is bd_warehouse's pattern (CSV row keyed by standard designation → geometry + named joints + hole helpers) and PartCAD's (YAML package with interfaces/requirements). A small team should define its own thin component record and borrow property names from ECLASS/AAS where convenient.

### Cited Findings
- OpenCASCADE has a built-in defeaturing operator, `BRepAlgoAPI_Defeaturing` ("intended for removal of the unwanted parts from the shape. The unwanted parts (or features) can be holes, protrusions, gaps, chamfers, fillets etc."); the caller must supply the faces that constitute the feature; options/limits are documented under `BOPAlgo_RemoveFeatures`. It is exposed in the Python OCP bindings used by CadQuery/build123d (the python-ocp source includes `BRepAlgoAPI_Defeaturing.hxx`) [search] — [OCCT reference: BRepAlgoAPI_Defeaturing](https://dev.opencascade.org/doc/refman/html/classBRepAlgoAPI__Defeaturing.html); [Debian python-ocp source](https://sources.debian.org/src/python-ocp/7.9.3.1%2B~cs7.9.3.1-1/OCP/BRepAlgoAPI.cpp)
- Known reliability problems: OCCT tracker issues report that the defeaturing class "alters the model topology in unexpected and unwarranted ways" and a case where the algorithm never finishes when removing a small fillet-created face; a Gmsh issue requesting defeaturing in its API was a feature request, not a shipped feature (as of the search result) [search] — [OCCT issue 33693](https://tracker.dev.opencascade.org/view.php?id=33693); [OCCT issue 33561](https://tracker.dev.opencascade.org/view.php?id=33561); [Gmsh issue 2868](https://gitlab.onelab.info/gmsh/gmsh/-/issues/2868)
- Library-side simplification precedent: bd_warehouse bearings are generated with "accurate external dimensions but simplified internal structure to avoid excess creation time"; FreeCAD Fasteners makes real threads optional because generating them is slow [1st-hand] — [bd_warehouse docs/bearing.rst](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/docs/bearing.rst); [FastenersWB README](https://raw.githubusercontent.com/shaise/FreeCAD_FastenersWB/master/README.md)
- Interface encoding precedent (build123d): parts carry named joints (`RigidJoint("a", self, Pos(...))`, `LinearJoint`, `RevoluteJoint`) and are mated by `connect_to`; fasteners expose `hole_locations`; bearings/inserts pair with `PressFitHole` / `InsertHole` and clearance/tap hole tables read from CSV (`clearance_hole_sizes.csv`) [1st-hand] — [open_builds.py](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/src/bd_warehouse/open_builds.py); [bearing.py](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/src/bd_warehouse/bearing.py)
- Mass/material when STEP lacks it: bd_materials provides representative density and `material.mass(volume_mm3=...)` but warns values are typical only and that detailed design should use the product data sheet [1st-hand] — [bd_materials README](https://raw.githubusercontent.com/gumyr/bd_materials/main/README.md)
- Caching precedent: text-to-cad converts each vendor STEP once to its `xbf` document and re-reads that ("many times faster than parsing the STEP"); PartCAD caches renders/models in memory, disk, memcached and S3 [1st-hand] — [text-to-cad SKILL.md](https://raw.githubusercontent.com/earthtojake/text-to-cad/main/skills/cad/SKILL.md); [PartCAD README](https://raw.githubusercontent.com/partcad/partcad/devel/README.md)
- Vendor-STEP modelling artefacts a verifier must expect (single fused solid for motor case + output; mating parts drawn overlapping, e.g. "a carriage drawn inside its rail") are documented by text-to-cad, with thresholds it uses (overlap must deepen by 0.6 mm beyond as-drawn to count as contact) [1st-hand] — [text-to-cad SKILL.md](https://raw.githubusercontent.com/earthtojake/text-to-cad/main/skills/cad/SKILL.md)
- AAS: IDTA 02003 "Generic Frame for Technical Data for Industrial Equipment in Manufacturing" is at v2.0 (March 2025); it is a submodel template whose central element is a set of properties made interoperable by dictionaries "such as ECLASS and IEC CDD"; semantic IDs can be attached to every element. IDTA published (Oct 2024) a guideline on how ECLASS is transported in the AAS, including data-type mapping. A ZVEI discussion paper proposes extending Technical Data with the component data needed for electric-drive *sizing calculations* [search] — [IDTA 02003 v2.0 PDF](https://industrialdigitaltwin.org/wp-content/uploads/2025/03/IDTA-02003_Generic-Frame-for-Technical-Data.pdf); [IDTA ECLASS-in-AAS guideline](https://industrialdigitaltwin.org/wp-content/uploads/2024/10/2024-10_IDTA_ECLASS_Semantic_Transport_ECLASS_in_AAS_1.0.pdf); [ECLASS news](https://eclass.eu/en/news/news/new-version-of-the-idta-submodel-technical-data-structure-and-use-of-the-submodel-with-eclass); [ZVEI Digital Engineering discussion paper](https://www.zvei.org/fileadmin/user_upload/Presse_und_Medien/Publikationen/2022/Mai/Diskussionspapier_Digital_Engineering/Diskussionspapier_Digital_Engineering_final.pdf)

### Inferences
- Recommended minimal component record (synthesis; fields chosen because each is needed by a specific verifier):
  - `id`, `family` (e.g. `linear_guide.profile_rail.MGN12H`), `standard_designation` (ISO/DIN/NEMA or vendor series), `suppliers[] {vendor, sku, url, price, stock, fetched_at}`.
  - `geometry {source: parametric|vendor_step, generator/ file hash, units, licence, redistributable: bool}` plus `proxy_geometry` (defeatured: no threads, no rolling elements, no logos) and `collision_geometry` (convex pieces) — three LODs.
  - `bodies[]` kinematic split (rail/carriage, screw/nut, rotor/stator, inner/outer ring) with the internal joint (type, axis, travel limits).
  - `interfaces[]` typed ports: `{name, type: bolt_pattern|shaft|bore|slot|face|press_fit_OD, frame (Location), params (thread, PCD, count, diameter+tolerance class, depth), mating_rule}` → maps 1:1 onto build123d joints.
  - `ratings {C, C0, Pu, n_max, M_x/M_y/M_z static moments, holding torque, torque_speed[] at (V, I), rated current, lead, backlash, max axial load, critical speed params, temperature range}` with `source_doc` and page reference for each value.
  - `mass`, `cog`, `inertia` (from datasheet mass; fall back to volume × density flagged `estimated`).
  - `verification {immutable: true, expected_overlaps[], keep_out_volumes[], required_clearances[]}`.
- Automatic mounting-feature detection on vendor STEP is feasible with plain B-rep queries for the cases that matter (cylindrical faces → axis, radius, depth; coaxial groups → counterbores; equal-radius parallel-axis groups on a plane → bolt pattern; largest planar faces → mounting faces; long cylinder protruding → shaft). No off-the-shelf open Python library for this was found; treat as in-house code, run once at ingestion, and store results in the record after an LLM/vision or human review rather than re-detecting each loop.
- Do defeaturing at *ingestion*, not in the loop: because `BRepAlgoAPI_Defeaturing` is face-driven and has known hang/topology bugs, wrap it with a timeout and a volume/bbox sanity check, and fall back to envelope substitution (bounding cylinder/box unions, or regenerate as a parametric proxy from datasheet dimensions). For bearings, linear carriages and ball nuts, a proxy model is more robust than defeaturing.
- Units: STEP carries its unit context, but mass/inertia do not travel reliably in AP203/AP214 exports; treat any mass in a vendor file as untrusted and prefer the datasheet value. (General practice; no source retrieved this session.)
- AAS/ECLASS are worth *naming alignment* only: adopting property identifiers (ECLASS IRDIs) for fields such as basic dynamic load rating makes later ingestion of manufacturer AAS files possible, but nothing found indicates maker-grade vendors (LDO, StepperOnline, OpenBuilds) publish AAS data.

### Gaps
- ISO 13584 PLIB, DIN 4000, STEP AP242 property/PMI carriage for catalog parts: no sources retrieved this session; the searches returned only AAS/ECLASS material.
- Open feature-recognition libraries for hole patterns (e.g. Analysis Situs was only mentioned in passing in a search result; capabilities unverified).
- Any open dataset of COTS mechanical components with ratings in machine-readable form (beyond the bd_warehouse CSVs and NopSCADlib tables): none found.
- Evidence on how much defeaturing speeds interference/FEA for typical vendor parts: none found.

## 5. Selection and sizing; LLM-based component selection research; how verification should treat COTS parts

### Takeaway
Open, maintained Python tooling for COTS sizing is thin: I found one ISO 281/ISO 76 deep-groove bearing calculator and one timing-belt script, and nothing packaged for ball screws, linear guides, stepper torque curves or extrusion deflection — these are a few closed-form equations each and should be written in-house as deterministic checkers. On the research side I found **no** 2024–2026 benchmark of LLMs selecting mechanical catalog parts; adjacent evidence (photonics, PCB) consistently shows inconsistent/invalid component choices unless generation is constrained to a curated database with an explicit out-of-catalog halt.

### Cited Findings

**Open sizing tools**
- `DGBBCalculator` (slehmann1): Python tool for deep-groove ball bearings covering static safety factor and basic rating life modified by reliability "as defined by ISO 76:2006 and ISO 281:2007"; depends on NumPy/pandas/Matplotlib [search; via a mirror page] — [DGBBCalculator mirror](https://github.imc.re/slehmann1/DGBBCalculator)
- PyPI `pybearing` is for bearing fault frequencies/envelope analysis, not ISO 281 life [search] — [pypi.org/project/pybearing](https://pypi.org/project/pybearing/)
- Ball-screw sizing: no Python library surfaced; references are vendor guides (Thomson "Selecting and Sizing Ball Screw Drives"; MISUMI technical page with the axial-load/torque/lead relation) [search] — [Thomson article](https://www.thomsonlinear.com:443/downloads/articles/Selecting_Sizing_Ball_Screw_Drives_taen.pdf); [MISUMI tech page](https://id.misumi-ec.com/pdf/tech/mech/p2799.pdf)
- Timing belts: a GT2-aware command-line Python/SciPy script for belt-drive parameters (centre distance from tooth counts) surfaced, plus engineering guides on required belt width [search] — [York Industries: finding the required belt width](https://www.york-ind.com/engineering/belts/finding-the-required-belt-width.html)
- Stepper torque–speed: no open dataset found; curves live in per-product PDFs (e.g. joy-it NEMA datasheets) [search] — [joy-it NEMA17-06 datasheet](https://www.joy-it.net/files/files/Produkte/NEMA17-06/NEMA17-06_Datasheet_2025-11-24.pdf)
- py_gearworks explicitly does not do gear strength/pitting calculations [1st-hand] — [py_gearworks README](https://raw.githubusercontent.com/GarryBGoode/py_gearworks/main/README.md)
- Rating data that *is* openly packaged: bd_warehouse bearing CSVs (C, C0, Pu, speed limits, mass, kr, f0) [1st-hand] — [bd_warehouse bearing CSV](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/src/bd_warehouse/data/single_row_deep_groove_ball_bearing_parameters.csv)

**LLM component-selection research (2024–2026)**
- Photonic IC design agents (arXiv 2508.14123, Aug 2025): the component-selection step "often picked inconsistent devices, and parameter mismatches were common"; errors persisted across GPT-4o, o1 and o3-mini, and with GPT-4o at temperature 0.1 [search] — [arXiv 2508.14123](https://arxiv.org/pdf/2508.14123)
- CircuitLM (arXiv 2601.04505, rev. Mar 2026): grounds generation in a curated component database and "raises an Out-of-Distribution flag, halts execution, and requests human review when a requested part is missing" [search] — [arXiv 2601.04505](https://arxiv.org/html/2601.04505v2)
- DRCY (arXiv 2603.15672, Mar 2026): agentic schematic review; a Selection Agent extracts manufacturer part numbers per component group and a separate retrieval stage fetches the datasheets for those parts [search] — [arXiv 2603.15672](https://arxiv.org/html/2603.15672)
- Retrieval analogues: an "ECLASS-augmented semantic product search for electronic components" paper reports dense retrieval + re-ranking outperforming lexical and foundation-model baselines; an EMNLP 2025 paper enriches a component database via web mining and uses hybrid search + LLM re-ranking to match documents to components [search] — [review of ECLASS-augmented search paper](https://www.themoonlight.io/fr/review/eclass-augmented-semantic-product-search-for-electronic-components); [EMNLP 2025 talk listing](https://underline.io/lecture/131795-automotive-document-labeling-using-large-language-models)
- Mechanical-domain agent papers surfaced treat component selection only as a workflow step, without a catalog-selection evaluation: "An LLM-enabled Multi-Agent Autonomous Mechatronics Design Framework" (arXiv 2504.14681, CVPR 2025 workshop); "A Multidisciplinary Design and Optimization (MDO) Agent Driven by LLMs" (arXiv 2511.17511; uses RAG for knowledge-grounded conceptualisation); "LLM Agent as a Mechanical Designer" (arXiv 2404.17525; truss design with FEM feedback) [search] — [arXiv 2504.14681](https://arxiv.org/abs/2504.14681); [arXiv 2511.17511](https://arxiv.org/abs/2511.17511); [alphaXiv 2404.17525](https://www.alphaxiv.org/abs/2404.17525)
- Industry claim (vendor blog, not peer-reviewed): AI tools often suggest part numbers that are discontinued or "look plausible but were never manufactured" [search] — [Z2Data insight](https://www.z2data.com/de/insights/using-ai-for-electronic-part-search-is-more-risky-than-you-think)

### Inferences
- Design rule supported by the adjacent evidence (CircuitLM, photonics paper): the agent must **never emit a free-text part number**. Selection should be a tool call that returns rows from the local typed catalog (`catalog.search(family, constraints) -> [component_id…]`), instantiation should only accept a `component_id`, and an out-of-catalog request should halt/escalate rather than improvise. bd_warehouse's `types()/sizes()` reflection is a small-scale instance of the same idea.
- Deterministic sizing checkers a gantry agent needs (each a short function; inputs = simulated loads from the motion/FEA verifiers, catalog ratings from the component record):
  - Rolling bearings: equivalent load P, L10 = (C/P)^p × 10^6 rev (p = 3 ball, 10/3 roller), static safety s0 = C0/P0, speed vs limiting speed. Data already in bd_warehouse CSV.
  - Profile rails: per-carriage equivalent load from forces and moments vs C, C0, M ratings; travel-life formula from the vendor catalogue.
  - Ball/lead screws: drive torque from axial load and lead with efficiency, column buckling and critical (whirl) speed from root diameter, unsupported length and end fixity, nut life.
  - Belts: tension from peak acceleration × moving mass, vs rated working tension for width/pitch, teeth-in-mesh, belt stretch/stiffness contribution to resonance.
  - Steppers: required torque (inertia × accel + friction + gravity) vs pull-out torque at speed for the chosen voltage/current, with a margin (the curve must come from the datasheet; holding torque alone is insufficient).
  - Fasteners: proof load by property class, preload, shear/tension utilisation, thread engagement length in aluminium/plastic.
  - Extrusion: beam deflection from catalogue I_x/I_y, or just FEA of the true section.
  (These formulas are standard engineering practice; I did not retrieve sources for each in this session — see Gaps.)
- How the verification loop should treat COTS parts:
  1. **Immutable**: hash COTS geometry at instantiation; any diff in a COTS solid after the agent's edit (boolean cut through a motor, drilled rail) is a hard failure. Only custom parts may be modified to fit.
  2. **Interface compatibility as type-checking**: each mate must connect compatible port types (M3 clearance hole ↔ M3 thread; 5 mm shaft ↔ 5 mm bore with stated fit; NEMA17 31 mm pattern ↔ matching pattern); screw length vs stack-up and thread engagement; tool-access/assemblability for each fastener.
  3. **Ratings vs simulated loads**: pull reaction forces/moments and speeds from the motion sim/FEA and evaluate the family-specific checker with a required safety factor; report utilisation per part.
  4. **Expected-contact allow-lists**: vendor geometry overlaps as drawn (text-to-cad evidence), threads vs holes, press fits — suppress via declared interfaces, not global tolerances.
  5. **Travel limits and keep-outs** come from the datasheet (stroke, belt path, cable exit), not from collision of simplified vendor solids.
  6. **Mass budget** uses datasheet mass; flag `estimated` masses.
  7. **BOM closure**: every solid in the assembly is either a custom part (with process/material) or resolves to a `component_id` with ≥1 supplier SKU; BOM rollup = count × price with `fetched_at`; availability check via distributor API where the part is electromechanical.
- For FEA, COTS parts are usually best represented as rigid/idealised connectors (bearing = spring or kinematic constraint, bolted joint = tie/beam) rather than meshed vendor solids; text-to-cad's FEA skill is explicitly limited to "an assembly of bonded parts" [text-to-cad README], which signals where the open tooling currently stops.

### Gaps
- No peer-reviewed 2024–2026 study measuring LLM accuracy at selecting **mechanical** catalog parts (bearings, rails, motors) or the rate of invented mechanical part numbers was found; MIT DeCoDE or similar groups' work on this specific task did not surface in searches. This is a genuine evidence gap, not proof of absence.
- Datasheet-extraction accuracy numbers (tables/torque curves from PDFs) for mechanical datasheets: none found.
- Open Python tools for linear-guide life, ball-screw sizing, stepper torque-speed modelling, bolt preload (VDI 2230-style) and extrusion deflection: none found; vendors (HIWIN, THK, Thomson, Tolomatic) offer web calculators/guides only.
- The sizing formulas listed under Inferences are from general engineering knowledge and should be cited from ISO 281/ISO 76 and manufacturer catalogues by the report writer if stated as fact.
- BOM/cost rollup and sourcing automation products (OpenBOM, Leo AI) appeared only as vendor marketing; not evaluated.

## 6. Reference/eval targets: complete open-source machines with BOM + CAD

### Takeaway
Voron (GPL-3.0; STEP + CAD in repo, BOM via web configurator) is the cleanest fully open gantry reference; Prusa i3-class printers are GPL-2.0 (MK3S repo) while the newer CORE One CAD is under Prusa's own restrictive "Open Community License"; RatRig V-Core 3 is CC BY-NC-SA 4.0 (non-commercial) and V-Core 4 CAD appears to be offered via an online Fusion viewer; PrintNC states CC BY 4.0; MPCNC is reported as non-commercial CC. For an internal eval set, licences that are copyleft or NC still generally permit using the designs as *reference targets*, but NC/OCL terms constrain commercial redistribution of derived data — check before publishing a benchmark.

### Cited Findings
- Voron 2.4: repo `LICENSE` is the GNU GPL v3 text; README: "The official release of the Voron 2.4 3d printer. You can find the BOM in the configurator located at the Voron Design website"; release zip at voron.zip; Stealthburner toolhead is maintained in a separate repo [1st-hand] — [Voron-2 README](https://raw.githubusercontent.com/VoronDesign/Voron-2/Voron2.4/README.md); [Voron-2 LICENSE](https://raw.githubusercontent.com/VoronDesign/Voron-2/Voron2.4/LICENSE)
- Voron Trident: GPL v3 `LICENSE`; README: BOM "in the configurator located at the Voron Design web site"; recommended sizes 250x250x250, 300x300x250, 350x350x250. Voron 0 repo also carries GPL v3 [1st-hand] — [Voron-Trident README](https://raw.githubusercontent.com/VoronDesign/Voron-Trident/main/README.md); [Voron-Trident LICENSE](https://raw.githubusercontent.com/VoronDesign/Voron-Trident/main/LICENSE); [Voron-0 LICENSE](https://raw.githubusercontent.com/VoronDesign/Voron-0/Voron0.2r1/LICENSE)
- RatRig V-Core 3: repo `LICENSE` is "Attribution-NonCommercial-ShareAlike 4.0 International" (CC BY-NC-SA 4.0); README is a one-line pointer to the project page [1st-hand] — [V-Core-3 LICENSE](https://raw.githubusercontent.com/Rat-Rig/V-Core-3/main/LICENSE); [V-Core-3 README](https://raw.githubusercontent.com/Rat-Rig/V-Core-3/main/README.md)
- RatRig V-Core 4.0/4.1: the RatRig wiki "files" pages say CAD is made available via the Rat Rig Fusion 360 online viewer and do not state a licence in the summary; RatRig publishes BOM pages on docs.ratrig.com (V-Core 4.0 BOM, V-Core 3.1 BOM); a different RatRig repo (V-Chonk) is CC BY-SA 4.0 [search] — [RatRig wiki V-Core 4.1 files](https://wiki.ratrig.com/products/v-core-4-1/files); [V-Core 4.0 BOM](https://docs.ratrig.com/v-core-4-0/bom); [Rat-Rig/V-Chonk](https://github.com/Rat-Rig/V-Chonk)
- Prusa i3 MK3S: repo `LICENSE` is GNU GPL v2; README: "Original Prusa i3 MK3S is a 3D printer project maintained by PRUSA RESEARCH" [1st-hand] — [Original-Prusa-i3 MK3S LICENSE](https://raw.githubusercontent.com/prusa3d/Original-Prusa-i3/MK3S/LICENSE)
- Prusa CORE One / CORE One L: Prusa released full CAD (STEP files and Fusion assemblies) under its new "Open Community License (OCL)", not GPL/CC; without a separate agreement the OCL restricts selling complete machines or commercial remixes based on the files; Fabbaloo argues it is "not a true open source license" [search] — [Prusa blog](https://blog.prusa3d.com/core-one-cad-files-release-under-the-new-open-community-license-ocl_127290); [Tom's Hardware](https://www.tomshardware.com/3d-printing/prusa-research-introduces-the-open-community-license-to-protect-open-source-3d-printing-hardware-new-rules-aimed-at-addressing-industry-abuses); [Fabbaloo](https://www.fabbaloo.com/?p=233470)
- PrintNC: the GitHub repo README says V2.1 is "outdated… Please use printNC Wiki for updated files and build guide… for now this repository should not be used", and "The PrintNC is completely open-source and operates under the CC BY 4.0 license"; steel-tube frame + 3D-printed parts CNC router [1st-hand] — [printNC README](https://raw.githubusercontent.com/threedesigns/printNC/master/README.md)
- MPCNC: a V1 Engineering forum thread describes the parts as downloaded "with a CC license… attribution, non commercial, share alike" (user description, not the licence text) [search] — [V1E forum: Is mpCNC open source?](https://forum.v1engineering.com/t/is-mpcnc-open-source/8150)
- bd_warehouse already contains parametric OpenBuilds parts and pre-built sub-assemblies (C-Beam actuator end with NEMA 23, coupler, bearing, lead screw; V-wheel assemblies; gantry plates) with joints — a ready-made code-CAD reference for an OpenBuilds-style linear axis [1st-hand] — [open_builds.py](https://raw.githubusercontent.com/gumyr/bd_warehouse/main/src/bd_warehouse/open_builds.py)

### Inferences
- Best eval targets for a gantry-designing agent, by suitability:
  1. **Voron Trident / 2.4** — CoreXY gantry on 2020 extrusion with MGN rails, GT2 belts, NEMA17s; GPL-3 STEP in repo; a human-curated sourcing-guide/BOM. Good "ground truth" for: BOM category coverage (does the agent's BOM contain the same *classes* of COTS parts with plausible sizes/counts), interface correctness (NEMA17 pattern, MGN9/12 hole spacing, M3/M5 hardware), and belt path/travel.
  2. **OpenBuilds C-Beam axis** via bd_warehouse — the only target that already exists *as build123d code with joints*, so it can be used for regression tests of the agent's own catalog/joint machinery with no licence friction (Apache-2.0).
  3. **PrintNC** (CC BY 4.0) — steel-frame CNC with ball screws and HGR rails; exercises screw/rail sizing under cutting loads; canonical files live on the wiki, not GitHub.
  4. **Prusa MK3S** (GPL-2) — simple bed-slinger with rods/LM8UU and lead screws; mostly OpenSCAD sources for printed parts.
  5. RatRig V-Core 3 (CC BY-NC-SA) and Prusa CORE One (OCL) — usable for internal reference with care; avoid redistributing derived datasets commercially.
- Voron BOMs live in a web configurator rather than a static file in the repo, so an eval harness needs a frozen snapshot (CSV) captured once and stored with the commit hash of the CAD release.
- GPL-3 on CAD files affects redistribution of the files and derivatives, not an agent that merely *compares* its output against them internally; publishing a benchmark that bundles Voron STEP would have to be GPL-3-compatible. (Licence-scope reasoning; not legal advice.)
